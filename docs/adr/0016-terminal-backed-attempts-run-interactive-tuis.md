# Terminal-backed attempts run interactive TUIs, captured by `script`

Terminal-backed attempts (ADR-0014) launched their harness in batch mode (`claude -p`, `opencode run`, `agent -p`), so the herdr pane was a real terminal running a one-way stream: the operator could watch but not steer. We now spawn the harness as a full interactive TUI — all three harnesses at once — so the operator types into the pane mid-run exactly as in a local session, while the engine stays oblivious to that input. Because a TUI refuses a piped stdout, the `| tee` wrapper is replaced with `script -eqfc '<harness cmd>' <stream-file>` (`-e` makes script's exit status the harness's, so the trailing exit-code write carries the real code; script otherwise exits 0), which supplies the PTY, passes the session through live, and records both directions to the Stream file; the prompt can no longer arrive as argv, so the engine waits for TUI readiness and types it in, with echo verification, retry, and a file-referencing fallback. Completion moves from "exit plus Outcome" to Outcome alone — a TUI deliberately stays alive after the agent declares done — while pane loss without a valid Outcome remains the crash signal.

**Considered options**: keeping batch mode and accepting follow-ups via harness streaming-stdin (`claude -p --input-format stream-json`) was rejected because it preserves the log pipeline but not the local-session experience the operator asked for; Console-side input (a send endpoint plus input box on the embedded terminal surface) was rejected for now because the herdr pane is already a real PTY — typing there is free — and the embedded surface stays deferred.

**Consequences**: for terminal-backed attempts the Stream file is a `script` typescript, not harness stream-json, amending ADR-0012's assumption for this path only (headless attempts are unchanged); the derived log is the ANSI-stripped transcript and now includes the operator's own keystrokes; grading, head-to-head judging, Vitals, and the log view keep working unchanged because they read the derived log; this resolves ADR-0014's deferral of "operator can type into the terminal" toward the herdr tab rather than the Console surface.

**Amendment (issue #58, the wrapper's `script` form is the platform's)**: `script -eqfc '<cmd>' <file>` is util-linux `script`. BSD `script`, which macOS ships, has no `-c` (the command's words follow the file) and flushes on `-F`, so the form above never started a harness on macOS: the tab opened with the right label and cwd, `script` rejected the flags on the wrapper's first line, the shell wrote `1` to the exit-code file and sat at its prompt, and no prompt was ever typed. The wrapper now chooses the recording form by platform, `script -eqF <file> <cmd words>` on darwin, each word quoted so the pane's shell hands script the exact argv (BSD script execs the words directly, where util-linux runs the `-c` string through a shell); `-e` and `-q` mean the same on both, so the exit-status semantics above hold unchanged. The line stays POSIX quoting and `$?`, which the operator's login shell (ADR-0014: zsh on a Mac) reads as bash does.

**Amendment (issue #58, a harness that dies on launch ends the attempt at once)**: the same report showed a second gap. A wrapper that dies on launch leaves a live pane at a shell prompt, which never ends, so the readiness wait ran to its timeout and reported a TUI that "never became ready" over a harness that had exited with a code of its own, and closed the pane that held the only record of why. The readiness wait now also watches the exit-code file, which the wrapper send clears beforehand so its appearance can only be this attempt's `script` returning, and checks it on a pane end too, since the two can land together and the harness's code is the truer ending (ADR-0014: neither observation trusted alone). An attempt whose harness exits before its ready frame ends at once with that code, the same ending a headless spawn that died on launch reports, and its pane stays open under ADR-0014's crashed-attempt rule, since when `script` itself refused to run the Stream file was never created and the pane is all there is.

**Amendment (issue #127, Blocking dialogs and the ending that names them)**: claude puts up screens before its prompt that hold the Launch until they are answered: the workspace Folder trust dialog in a directory it has never seen, the bypass-permissions warning, the managed-settings approval. The readiness wait answered the first by a button label, "No, exit", with a blind down-then-enter and no check that the highlight had moved, and re-sent the pair on every poll while the dialog stood; the label also sits on the other two dialogs, so the same keys could go at a warning the engine has no business accepting. The wait now knows each dialog by a line of its own body, read from Claude Code 2.1.276 and kept in one table with the build named; it answers only the Folder trust dialog, once, by moving the highlight, reading the pane back and confirming only when the highlighted row names "Yes, I trust this folder", at the prototype's pacing, and restarts its clock after the answer, since the timeout exists to catch a wedged harness and an answered dialog cost the harness nothing. A dialog only the operator may answer, a highlight that would not move, or a dialog still standing after its answer ends the Launch at once as `blocked`, not at the timeout. The ending is legible: the crash reason says which dialog stood on the pane and what was done about it, the pane's last frame is written into the derived log when the drain left it empty, so the crash event's tail and the interrupt body show the dialog rather than a blank, and the crash interrupt body now leads with the crash reason for every crash, which it had never carried. A readiness failure stays a crash, not a retried Botched launch: a dialog the engine could not clear will stand again on retry. ADR-0025 removes the Folder trust dialog from the pool worktrees before it can appear; this handling is what stands behind that seed.
