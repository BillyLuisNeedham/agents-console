# A persist failure interrupts instead of killing the pool

The drive loop sat inside one try/catch whose fatal path closed the checkpoint store, settled the drive, and rethrew, and the caller swallowed that rethrow. One error of any kind, including a single failed checkpoint write, therefore killed the drive permanently while the server kept serving the last snapshot as if the run were live. The Console's frozen running phase was a lie, and nothing on disk said what had killed the loop. This was issue #26 (https://github.com/BillyLuisNeedham/agents-console/issues/26); the design is `docs/specs/2026-09-02-no-silent-dead-drives.md`, which names the failure mode a dead drive.

We decided that a persist failure is not a reason to kill the drive. A persist that throws at a super-step boundary, the Review gate, or the final closing persist is retried three times with 50/100/200ms backoff, four attempts in all. On success the drive continues as if nothing happened. On exhaustion the pool raises a run-level persistence interrupt (ticketId `PERSISTENCE`, the run-level convention `REVIEW` already established), whose body names the attempt count and the last error, and the drive settles quiescent with the store still open, the closing persist having retried once more before the gate settles. The human answers the interrupt once the store is healthy; the drain persists the answered state itself, and the resumed drive's next boundary write carries the run forward.

Three alternatives were weighed. Crash loudly: let a failed persist kill the process so the human restarts from disk. Restart-from-disk is a real escape hatch, but it turns every transient hiccup into manual recovery, and it does not distinguish a flaky write from a dead drive; the old design was worse than either, since it killed the drive without any crash surface at all. Retry forever: no human is ever bothered, but an unbounded backoff hides a permanent fault (a full disk, a locked database) behind an endless loop, and the run never names its problem. Silent swallow: the prior design itself, one transient error permanently killing the drive while the server kept serving the last snapshot as live; this ADR exists to forbid exactly that.

**Consequences**: a boundary persist failure can no longer reach the drive's death path; a persist that exhausts into the interrupt produces no errors.jsonl record, no pool log line, and no dead phase, and the tests pin that. Any error that does kill the drive reports through one shared mechanism before the waiters settle: a durable JSONL record at `runs/errors.jsonl` in the pool directory, a `pool dead:` line in the pool log, and a terminal dead phase on `RunPhase`, carried through the server snapshot to the Console, where dead renders as terminal. The dead phase is not a closing-gate outcome; the closing gate never runs on a dead drive, which is the distinction from stalled the glossary records, and a drive that dies without emitting it is lying. The drive closes the store only at the closing gate or on drive death; the run handle's `close()` remains for callers tearing the run down, and restart-from-disk remains the escape hatch. Testing the fix needed one seam: the checkpoint store is substitutable at pool start (the `CheckpointStore` interface behind `RunOptions.store`, defaulting to `SqliteCheckpointStore`). The answer drain persists each answered interrupt's state change itself and does not retry, so a persist failure in the boundary drain can still kill the drive and reports dead like any other error.
