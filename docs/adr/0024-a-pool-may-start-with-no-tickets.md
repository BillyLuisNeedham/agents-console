# A Pool may start with no Tickets and grow from live work

Every Pool until now arrived written: `to-tickets` wrote the Ticket files, `my-console-runner` pointed the Console at them, and the first super-step ran what was already on disk. Conversations (ADR-0018) and Enlist (ADR-0021) made a second shape possible and then left it undescribed. An operator opens herdr panes by hand, talks to the agents in them, Enlists the ones that turn out to matter, and lets those Conversations Spawn the Tickets, so the Pool is a product of the work rather than a plan for it. The engine has accepted that shape since the Conversations work: an empty ticket directory beside a `conversations/` directory boots, and the presence of that directory is the opt-in. No document said so. `CONTEXT.md` defined a Pool as "the set of tickets one Console run works", which is false for such a Pool, and `my-console-runner` step 1 told the operator that an empty pool is a reason to stop. The path worked and the prose forbade it, so it was reachable only by an operator who knew the code.

We decided a **Seeded Pool** is a Pool that starts with no Tickets, named in `CONTEXT.md` beside Pool, and a first-class path in `my-console-runner` rather than a deviation from it. The opt-in stays exactly where the engine already has it: a `conversations/` directory, which may be empty, separates "this Pool hosts Conversations" from the "no Tickets written yet" mistake that the bare refusal exists to catch. What changes is that the operator's intent is asked before detection rather than inferred from disk, because an empty ticket directory means opposite things on the two paths and only the operator knows which one they are on. The skill creates both `issues/` and `conversations/` on the Seeded path, and the engine creates the ticket directory on demand when an enlisted Ticket is written, so that Enlisting a pane as a Ticket into a Pool that booted without one no longer fails.

The alternatives were a sibling skill and inference from disk. A sibling skill was rejected because the two paths differ in one question and diverge nowhere after it: the interview, the config, the templates and the launch are one body of prose, and both skills would be user-invoked, so neither could reach the other and the shared two hundred lines would be copied and would drift, exactly as `my-console-runner` and `my-issue-runner` already have. Inference from disk was rejected because it silently converts the mistake the refusal exists to catch into a supported path: a Pool whose Tickets were never written looks identical on disk to a Pool that wants none, and the difference lives only in the operator's head.

**Consequences**: `my-console-runner` asks which kind of Pool is being started before it detects anything, and its empty-pool refusal fires only on the ticket path; its detection brief reports an empty ticket directory as the point rather than as a fault, and herdr matters more on this path than on the other, because Enlist is how the Pool grows. The one operator-facing refusal, in `engine/pool.ts`, names the term. `AGENT.md` is a quieter file here than on the ticket path: it reaches a Ticket the engine launched itself and nothing else, so on a Seeded Pool nobody the operator Enlists ever reads it, and it is written for the Tickets the Conversations Spawn. Question 3 of the interview has nothing to override at setup time, so `assign` starts empty and gains entries by hand as Spawned Tickets arrive, which the boundary reload of ADR-0018 already allows without a restart. A Seeded Pool is otherwise ordinary and stops being seeded at its first Spawn: no new lifecycle, no new storage, no new card lane, and nothing in the scheduler, the merge machinery or the Console distinguishes one afterwards.
