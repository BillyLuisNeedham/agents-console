# The Console commits a render by morphing the DOM, not replacing it

The Console's renderers have always been pure functions of the projected model (ADR-0006 and the Console session's contract in `CONTEXT.md`): every snapshot, every Vitals tick and every terminal peek called `render()`, and `ConsoleView.render` threw the page away and built it again with `root.replaceChildren`. That was the right first shape, since a renderer that rebuilds from scratch cannot drift from the model, and the doc comment in `view.ts` said so. What it cost only showed up as the page grew stateful. Nothing on screen survived a rebuild on its own, so each thing an operator noticed vanishing got its own rescue written around the swap: the attempt log pane's pin and reading position (`log-pane.ts`), the focused field and its caret (`focus.ts`, PR #123), the canvas pan and its pointer listeners (`bindCanvas`), the fullscreen class on the Detail, and three `cancelDrag` calls so a tick landing mid-drag failed cleanly instead of strangely. Nine regions the Console actually renders scroll (`styles.css` names fourteen, five of them dead selectors), and one of them was rescued. The others, the Detail body, both trays, the enlist picker and the log drawer, snapped to the top every two seconds, which is the flicker-on-scroll the operator reported. The next rescue would have been one more hand-rolled one.

We decided the renderers stay exactly as they are, pure and rebuilding their whole subtree with `h()`, and only the commit changes: `ConsoleView.render` builds the new tree as before and then calls `morph(old, new)` (`ui/src/morph.ts`), which walks the two trees together and patches the live one in place, so a node that is unchanged is the same object before and after, and one whose text or attributes changed is edited rather than remade. Children carrying a `key` (rendered as `data-key`) are matched by key so lists reorder by moving nodes; unkeyed children match by position and tag. Properties that `h()` sets as properties, the `on*` handlers, `checked`, `disabled` and `value`, are re-assigned on every patch so the closure that fires is always the one from the latest render. Scroll positions, focus, caret, hover, CSS transitions and in-flight drags survive because the nodes they belong to do. The morph is written in this repo, roughly two hundred lines with its own tests, not vendored: the surface it must cover is the one `h()` produces and nothing else, and the quirks it has to know about, handlers as properties and `value` as a live property, are this codebase's.

**Considered options**: patching only the region a timer owns (the Vitals tick touching only Vitals nodes) was rejected because the SSE snapshot, the most frequent trigger while a pool works, would still rebuild the whole page, so scroll would still jump at exactly the moments the operator is reading. Generalising the rescues further was rejected because it is the pattern that produced this problem: every rescue is a list of the things someone has noticed so far, and the list stopped at one region of nine. Vendoring `morphdom` was rejected because six hundred lines in another style, in a UI that has one runtime dependency and an ADR declining xterm.js, would read as a framework, and it does not know how `h()` attaches handlers. A DOM test environment is a new cost the repo had avoided: the bun tests ran without a `document` by design, and a morph is the first thing here whose behaviour *is* the DOM. `happy-dom` is registered for the UI tests, and a headless-Chromium harness (`ui/harness/`) mounts the real `ConsoleView` and proves, in a real layout engine, that scroll, focus, caret, canvas pan and node identity survive repeated renders. The harness is run by hand, not by `bun test`, because it needs a browser on the box.

**Consequences**: renderers must keep producing the whole subtree from the model on every call; a renderer that mutates the live DOM outside a render, or that caches an element across renders, now fights the morph instead of being discarded by the rebuild. Anything that attaches a listener with `addEventListener` on a node it just built must either become an `on*` prop through `h()` or guard against binding twice, since the node now persists. Lists whose rows can reorder or be removed from the middle need a `key`, or the morph will rewrite every row in place, which is correct but loses that row's scroll and focus. The harness proved the focus rescue, the log pane's reading-position restore, the Detail's post-render fullscreen fix-up, the canvas listener re-attach and the three drag cancels redundant, and they are deleted; drag state is rendered from the stores now, so a tick landing mid-drag draws the drag instead of aborting it. Three post-commit steps remain and say why: the log pane's tail pin and prepend anchor (the pane is one text node, so the browser's own scroll anchoring has nothing to hold when earlier lines are prepended), and the canvas's edge redraw and node map refresh (edge routes need the cards' laid-out positions, which exist only after commit). The Vitals tick asks for a render only when the "Ns ago" copy it would show has changed.

**Amendment (issue #157)**: a render is now asked for, not called. Every store's change goes through one render loop (`ui/src/frame.ts`) that commits at most once per animation frame, so a burst of snapshots, Vitals answers and peeks paints once; the tab title and favicon still update at once, since a hidden tab gets no frames. Two regions opt out of the morph's walk: the edge layer carries `KEEP_CHILDREN`, because the canvas updates its paths in place, keyed by source and target, after commit; and an `h()` node given an `html` prop (the rendered Spec) is skipped while its markup is unchanged.
