# A pool-config gap pauses the one ticket as a config interrupt, and an inherited Assignment falls through to the defaults field by field

Issue #118 (https://github.com/BillyLuisNeedham/agents-console/issues/118) found a running pool wedged by one ticket. An enlisted Conversation (ADR-0021) records no model, because herdr found the pane as it was and the engine never launched it. A Ticket the Conversation proposed inherited that Assignment, and since ADR-0010 a spawned ticket took its parent *instead of* the pool defaults, the empty model stayed empty. ADR-0013 chose to let an unassigned ticket render on the canvas and fire the pool-config error at spawn time, "so the run dies naming the ticket". It did: `harnessCommandFor` threw inside the super-step, the drive died, the checkpoint store closed with it, and every other pending Interrupt became unanswerable with `Database has closed`. The ticket's marker had already flipped to in-progress before the launch, so it sat on disk as a running ticket with no attempt behind it, its downstream tickets blocked behind it, and a restart refused to boot because the same empty model kept the Conversation out of the boot seed. Recovery took hand-edited markers and records and three restarts.

We decided two things. First, inheritance is field-wise all the way down: a spawned ticket, a grader and a head-to-head resolve each field as request, then parent (or build), then the pool defaults, and an empty string is no value. A parent that names a harness and no model hands its children the harness and lets the defaults supply the model, which is what the operator's defaults block is for. The boot seed follows the same rule and seeds a Conversation with whatever fields it has. Second, a ticket that would still schedule with no harness or model is caught at the plan, before its marker flips, and pauses as a `config` interrupt on that one ticket: an engine-voiced Interrupt like persistence, naming the missing field and the console.json fix, holding the ticket at checkpoint status so the ready set skips it. Resume returns the marker to ready, and the boundary's config reload (ADR-0018) re-resolves it from the edited file; resume with the file unchanged simply raises the interrupt again. The drive never dies for a config gap, so the other tickets keep running and the other Interrupts stay answerable.

We rejected keeping ADR-0013's die-loudly rule with a rollback of the marker on death. It fixes the phantom in-progress ticket but leaves the store closed and the run over, for a gap the operator can fill in one line; loud is right, terminal is not. We rejected making an enlisted Conversation take the defaults for its own model. Its card would then name a model the pane is not known to run, and the record is meant to read as found. We rejected a new marker status for the held ticket in favour of the existing checkpoint status: the ready-set rule, the rehydrate rules and the Console already treat a checkpointed ticket correctly, and a `config` record lost from the store comes back at boot as a plain checkpoint interrupt whose resume does the same thing. `harnessCommandFor` keeps its throw as the last-resort guard behind the plan-time check.

**Consequences**: `config` joins the interrupt kinds, with a resume-only form in the Console and an `unassigned` event on the ticket naming the missing field; the enlist teaching Turn now states the Conversation's own Assignment and the pool defaults and points at the `my-console-citizen` skill, so an enlisted agent can choose an `assign` on purpose or ask the operator in the pane; `assignment.test.ts`'s "never the defaults" pin is gone. ADR-0013's spawn-time death and ADR-0010's "parent stands in for the defaults" are amended by this record; the Assignment and Config reload glossary entries describe the fall-through and the pause.

**Amendment (2026-10-03, issue #116)**: a spawned ticket's chain gains a layer. Field by field it now resolves as request (the operator's `console.json` `assign` entry), then the proposal's own requested Assignment (its `assign`, never `verify`), then the parent, then the pool defaults. Reassign names a field the proposal supplied as `requested`.
