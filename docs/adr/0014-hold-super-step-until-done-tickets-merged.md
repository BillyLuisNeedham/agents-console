# Hold the whole super-step while any done ticket is unmerged

A ticket's marker is written `done` at attempt exit (`engine/engine.ts:2562`, `:2905`, the lone-attempt and selection completion paths), before its `pool/NN` branch merges to main. The ready set (`readySet`, `engine/engine.ts:368-387`) unblocks downstream tickets on that marker alone, so a dependent ticket could spawn against a main that did not yet contain its blocker's work — ticket 15 spawned while ticket 10 sat behind a merge conflict. This was issue #41 (https://github.com/BillyLuisNeedham/agents-console/issues/41).

We decided the scheduler computes no ready set at all while any ticket is done-but-unmerged: the whole pool pauses for merge hygiene, so every ticket in the next super-step starts from a main that contains all finished work. The hold engages whenever a ticket has `marker=done` and its `pool/NN` branch is not in its merge target, regardless of whether that target is main or a feature branch, and it applies everywhere the ready set is computed — the main scheduling loop, verify flows, and selection runs alike, one rule on one code path.

The hold lifts in three ways: a merge lands (the operator approves the existing merge-approval interrupt, or merges manually from the CLI — the next ready-set computation simply sees it landed); a done ticket's branch vanishes without merging, which reads as landed the same way `mergeBranch` reads a human finishing the job by hand — an accepted operator-trust path, not a gap, since the Console's reject path is the proper abandon route and an operator force-deleting a branch outside the Console is trusted to know what they're doing; or the merge is rejected, which reopens the ticket so it no longer counts as done. Tickets already running when the hold engages finish undisturbed; the hold withholds only spawning. No new persisted state records the hold — it is derived on demand, including at startup, by scanning markers for done tickets whose branches are unmerged, consistent with ADR-0007's derive-server-side pattern. The ready set's entry point derives the hold once and returns it alongside the ready set, so the pool-wide caller cannot mistake a hold that lifted between two derivations for a stop — a manual CLI merge landing in that gap would otherwise silently stop the pool with ready work unscheduled. Engine-run flows keep their wait-and-recompute loop. No new "held" interrupt is raised either: the existing merge-approval interrupt is the signal and the action, while the Console card shows a "done, merge pending" label (via `EnrichedTicketState`, `engine/server.ts:78-87`) so a held pool shows why it is held.

**The pause is a wait, not a quiesce.** A held pool's drive loop stays alive: it polls the derivation on a short cadence, drains queued answers as it waits, and computes the ready set fresh the moment the hold lifts. Quiescing instead would strand a manual CLI merge behind a drive that already exited, contradicting story 6 (unstick the pool without touching the Console), and would strand an approval the same way. The phase stays `running` while held; the pool settles only after the hold clears, so the existing quiescent/done/stalled semantics are untouched.

**The hold outranks the engine-id pass-through.** The check sits first in `readySet`, before ticket 01's clearing of engine-run proposals. Engine-run tickets — a verify round's graders and the selection run's head-to-head judge — reach `done` but run in the main checkout with no branch and so can never merge; the hold excludes them explicitly by the engine-ticket id check, by rule, not incidentally via the missing-branch reading. A withheld round waits the hold out through the same drain-and-poll helper and then recomputes; an all-engine proposal returns empty for no reason but the hold. Draining mid-fan-out is safe precisely where the boundary drain is safe (ADR-0004): at every wait site every attempt has exited and the super-step join is done, so no answer can be undone and no in-flight spawn can race a merge, and without the drain the pause would deadlock against the very approval that lifts it, since queued answers otherwise process only at the boundary the paused fan-out never reaches.

**The resolver re-run is the one spawn that bypasses the entry point.** The spawn-path audit behind "everywhere the ready set is computed" found adoption at the boundary, grader re-spawn rounds, the head-to-head judge, and review-reject re-runs all routing through `readySet`, where the hold withholds them alike, and answer processing never spawning an attempt; the resolver's re-run of a conflicted ticket (`handleMergeConflict`, `runResolver` in `engine/engine.ts`) is the named exception. The engine spawns it inline at merge time, after the join and while the hold's condition already stands, deliberately: gating it through the entry point would deadlock the hold against its own escape path, because the hold lifts only when the merge lands or the ticket reopens, a conflicted merge cannot land, and the resolver is what stages the resolution the approval lifts.

**Rejecting a merge reopens the ticket.** The merge-approval interrupt's reject now discards the resolver's staged resolution and sends the ticket's marker back to ready, instead of the old conversion to a manual-resolution interrupt with the ticket still done. Reopening is what lifts the hold; the parked branch is reused by the re-run, the way a review-reject re-run reuses one, and the rejection note rides along as a durable resume note. The by-hand path stays on the merge-conflict interrupt: resolve in the checkout and resume, or merge from the CLI and let the derivation observe it.

Alternatives weighed: gating per-ticket (unblock a dependent only when its specific blocker is merged) is finer-grained but keeps two facts the scheduler must join per ticket and leaves a partially-unmerged pool scheduling new work; holding was chosen for simplicity and for the stronger invariant that a super-step always sees fully-merged main. Draining pending approvals before computing the ready set narrows the window but loses the race whenever the operator is slow, so it cannot be the mechanism. Keeping per-ticket gating plus the hold was rejected as redundant once the hold exists.

The outcome channel is unchanged: a blocker's Outcome JSON still carries its result downstream, only the timing changes: downstream tickets now wait for the merge as well as the marker. The pinned test that asserted a downstream ticket receives its outcome even when the merge conflicted is rewritten ("holds a downstream ticket until its blocker's conflicted merge lands, then passes the outcome through", `engine/engine.test.ts`) to assert the downstream ticket waits.

The card label is one server-side derivation of the same fact, read through the enrichment seam: a ticket whose snapshot status is `done` and whose `pool/NN` branch has not landed in the merge target carries `mergePending` on `EnrichedTicketState`, and every UI surface renders it as "done, merge pending" without probing git itself. The merge target is the pool checkout's current branch at derive time, so a feature-branch target holds the label main would clear. A missing branch reads as landed, the same reading `mergeBranch` applies: the engine deletes the branch once its merge lands, and a ticket that ran in the main checkout never had one (engine-run tickets are excluded by the engine-ticket id rule, not by this reading). Because the fact is derived on demand, it is re-derived at serve time too: a manual CLI merge while the pool sits quiescent raises no snapshot, so `/api/state` and a stream connect re-derive before serving, and a Console opened after such a merge sees the label gone.

**Consequences**: "done" no longer means "downstream may start"; it means "work finished, merge pending or landed". The spawn-time warning about unmerged blockers was expected to become dead code and be removed, but no such warning exists anywhere in the codebase, past or present: there was nothing to remove, and no code path contradicts the hold. The spec's named test that running attempts finish while held is the same vacuity pattern: no such test was written, because none can be, the hold being evaluated only where ready sets are computed, which happens only after the join of the super-step (main loop), the fan-out (graders), or the grading round (judge), so no attempt is ever in flight when the hold is consulted and "running attempts finish undisturbed" is true by construction. A stuck merge now stalls the entire pool, not just dependents, deliberate: the operator's merge queue is the bottleneck the hold makes visible, and the escape hatches (approve, reject, manual merge) are the controls that already exist.

**Amendment (the hold rides the snapshot; ticket 05 of #54)**: "it is re-derived at serve time too" above described a second derivation, the server's own copy of this one, run from git on every `/api/state` and every stream connect. The two had already drifted by one rule: the engine skipped engine-run tickets explicitly, the server relied on the missing-ref reading to skip them. There is now one derivation, in the engine's Merge hold module, and the hold set rides the snapshot beside the assignments (ADR-0013), derived fresh at each emit and never persisted, which keeps the "derived on demand" rule above intact. The serve-time case the sentence existed for, a manual CLI merge that raises no snapshot, is covered engine-side instead: while the emitted hold set is non-empty the engine re-derives on a slow cadence and emits when the set changes, and when the set is empty nothing runs. The replay surfaces serve the last snapshot verbatim and spawn no git. A dead or closed drive stops the watch, so that case waits for a restart, as everything else does.

**Amendment (one wait-and-recompute rule; ticket 06 of #54)**: "Engine-run flows keep their wait-and-recompute loop" above left two copies of the same rule: the super-step boundary's (ready set first, then wait, then the whole boundary again) and the engine-run flows' (wait, then recompute, then wait again if the recompute finds the hold re-engaged). There is now one rule in the Merge hold module, taking a hold host and a recompute callback, and both callers use it: the boundary's recompute is the whole boundary, the engine-run flows' recompute is their spawn set. A hold that re-engages in the gap between the wait's exit and the recompute is a re-wait in both, never an empty set, and that rule is pinned once, by a scripted hold host, in the module's own tests; the hand-made session that pinned it before is gone.
