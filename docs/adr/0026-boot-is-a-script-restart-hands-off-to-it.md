# Boot is a script, Restart hands off to it, and Machine defaults live in one file

Every Console until now was started by an agent. `my-console-runner` asked the same eight questions on every pool, wrote `console.json` and the prose files, then ran a launch sequence that existed only as a page of instructions inside the skill, so a relaunch of a pool whose config had not changed still cost a conversation and the operator's time answering questions whose answers had not changed either (issue #121). The config it wrote could then only be changed by hand: the Console displayed it and offered nothing to edit, and a boot-only key such as the port or the terminal mode needed the operator to find the server's pid, kill it, and run the skill again. The machine's own defaults were split across three files that grew separately: a two-line `~/.issue-runner` the engine read for the resolver, a one-line `~/.console-runner` only the skill read for the engine path, and the Setups directory.

We decided that **Boot** is a script, `agent-console`, not a skill: it prefills from the pool's own config, then a chosen Setup, then Machine defaults, then detection, asks only for what is still missing, and starts the server. The skill keeps the one job a script cannot do, authoring the pool's prose. **Pool settings** are edited in the Console, through routes that write the same file the engine already reloads at the super-step boundary (ADR-0018), so the assignment slice takes effect without a restart and the boot-only keys are badged until one. **Restart** is the server stopping itself exactly as a Stop does (ADR-0019), farewell and all, and then handing off to Boot for its own pool with every answer taken from what is on disk. **Machine defaults** are one JSON file under `~/.agent-graphs/`, edited from the same pane; the two legacy files stay readable as a field-by-field fallback so a machine that never wrote the new file behaves as it did.

For Restart the alternatives were the server re-executing itself and an in-process reload. Re-executing itself was rejected because it repeats the launch sequence a second time in a second place, and skips the build check: the Console serves `ui/dist` from disk, and a restart is precisely the moment a stale build should be caught, which Boot already does on every start. An in-process reload was rejected because the boot-only keys are boot-only for a reason: the port is bound, the terminal mode decided where every tab lives, and the roster was baked into prompts already running; re-deriving all of that inside a live process is the whole server's startup written a second time with the old state still in memory. Handing off to a script the operator can also run by hand keeps one launch path, so a restart from the Console and a launch from a shell cannot drift apart. For the defaults file, keeping the two legacy files and adding a third was rejected because each new field would have needed a home chosen by hand, and replacing them without a fallback was rejected because every machine that has run a pool has both files and none has the new one.

**Consequences**: the server process exits on a Restart and a different process serves the pool a few seconds later, so the tab that asked follows by polling for the new server and moves to a new port if the settings changed it; every other tab sees an ordinary stop and its usual retry finds the relaunched server. Boot must therefore tolerate the old lock still being held for a moment, and does, by waiting for `runs/server.pid` to go before it starts. A Restart while Attempts are live is allowed behind the same inline confirm as Stop and treats them as any restart does: headless Attempts are stopped with the server (ADR-0017), terminal-backed ones stay in their tabs and are reconciled at the next boot. The skill's launch prose is gone, and a pool started from a shell and one restarted from the Console are indistinguishable on disk. `~/.issue-runner` and `~/.console-runner` are read but never written again; the Settings pane writes only the new file.
