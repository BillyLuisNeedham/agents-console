# Assignments belong to Attempts; the config's assignment slice reloads at the super-step boundary

`console.json` was read once at `startPool` and each ticket's Assignment was resolved once, at first sighting, and cached for the life of the run. Changing a ticket's harness, model, or drivers therefore meant a server restart, which kills the Attempt in flight and discards its work. Spawned tickets made this unfixable by pre-flight edit: their ids do not exist at boot, and the engine froze their Assignment at the very boundary that adopted them, before the operator had seen the card. This was issue #63 (https://github.com/BillyLuisNeedham/agents-console/issues/63).

We decided two things. First, an Assignment belongs to an Attempt, not a ticket: it is resolved from the current config at the super-step boundary that plans the Attempt. An Attempt in flight never changes; any ticket with no Attempt in flight (a fresh Spawn, a ticket resuming after a checkpoint, a ticket sent back by Review) takes the current config at its next boundary. Graders, head-to-head, and the merge resolver already worked this way, so the engine is now consistent rather than newly inconsistent. Second, the engine re-reads the assignment slice of `console.json` (`defaults`, `assign`, `resolver`) at the same boundary seam where queued answers drain and Spawn proposals are adopted (ADR-0004, ADR-0010). Roster, agents, selection, terminal, and port stay boot-frozen; terminal and port in particular must never move under a live run.

A file watcher was rejected: the repo already chose polling over `fs.watch` for pane liveness, and a watcher would land edits mid-super-step, where the join rebuilds state from a pre-flight snapshot and would undo them (the same reason ADR-0004 rejected mid-step answer processing). A reload endpoint or Console editor was deferred: the file is the source of truth, editing it is enough, and the badge already reflects the engine's derivation (ADR-0013). (Issue #126 later added that editor as Reassign: the Console writes a ticket's assign entry through the server, and the engine still picks it up only at this boundary, so nothing here changed.) Keeping the per-ticket freeze and only reading the file for unseen ids was rejected because it does not fix the spawn case at all.

**Consequences**: a reload is atomic. The new file is dry-run against every reassignable ticket; a parse error, unknown harness, or bad `verify` rejects the whole reload with one pool-log line naming the cause, and the previous config stands. The same bad content is logged once, not every boundary. A ticket whose next Attempt resolves to a different Assignment than its previous one gets a `reassigned` event in its Ticket log, so a run that changed model halfway is visible in forensics. A ticket edited while its Attempt is in flight sees nothing until that Attempt ends, by design.

**Amended by ADR-0029 (issue #149)**: the Spawn caps (`spawnCaps`) reload with the assignment slice. A Pool settings save on a pool with no drive in flight runs the reload at once, since an idle pool reaches no boundary.
