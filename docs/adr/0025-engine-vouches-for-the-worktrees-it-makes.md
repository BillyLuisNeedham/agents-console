# The engine vouches for the worktrees it makes: claude's Folder trust is seeded, never withdrawn

An interactive claude started in a directory it has never seen opens on its workspace trust dialog and waits for a human. Every pool worktree is such a directory: `worktreePathFor` gives each Ticket, verify candidate and Conversation a fresh path under the repo's `pool-worktrees` root, so on a `terminal: herdr` pool every claude Attempt met the dialog on its first launch, inside the readiness wait's 60 s budget, and on this machine claude takes about 30 s to paint its first frame before the dialog can even be answered. The engine's answer to the dialog (ADR-0016's issue #127 amendment) races it with paced keystrokes, and a race is the wrong shape for a screen the engine knew was coming: the engine created the directory, one call-stack level before the tab opened, so it knows the path before claude does. Two pools had failed on this, one before the handler existed and one worked around by hand-writing trust entries for six worktrees and their retry variants into claude's config before the next super-step, which worked.

We decided the engine **vouches for the directories it makes**: before a terminal-backed claude Attempt's tab opens, when its cwd is a pool worktree, the engine records `hasTrustDialogAccepted: true` for that path (and its realpath, when they differ) under `projects` in `~/.claude.json`, the per-directory record claude reads to skip the dialog. The write mirrors claude's own: the whole file re-read, the one entry added or flipped, the result written to a sibling temp file and renamed over the original, claude's own formatting so a diff of the file shows only the entry. The seed is **add-only**: nothing is ever removed, and a directory already trusted is left untouched. The seed's outcome rides the `spawned` event, so a launch that met the dialog anyway can be read back against what the seed did. The operator's own checkout is never seeded: a lone ready Ticket runs there, and vouching for the operator's project is a different act from vouching for a directory the engine created. The file is found the way claude finds it: under `CLAUDE_CONFIG_DIR` when that is set (confirmed on 2.1.276), else the home directory. A machine where claude has never run (no config file), or a config that does not parse, is left alone and the launch proceeds; the pane's dialog handling stands behind the seed for those cases and for a seed another claude session's write overtook, a narrower window than the prototype feared, since claude's own saves take a lock and re-read the file first.

Three alternatives were rejected. Answering the dialog in the pane as the only path was rejected because it races a screen the engine can foresee, spends a budget already half gone on first paint, and depends on button order and key pacing that have drifted once already; it stays, hardened, as the fallback. A claude flag or environment variable was looked for and does not exist: `--print` skips the dialog but records nothing, and the only trust-seeding switch in the binary belongs to Anthropic's self-hosted runner, which seeds the same key the same way. Pruning the entries the engine added when their worktrees go was rejected because claude never prunes the map itself, a stale entry for a directory that no longer exists is inert, and deleting from another tool's config is a larger act than adding to it. The cost accepted is that the engine now writes another tool's config file for the first time, where until now everything it wrote under the home directory was its own (`~/.agent-graphs/`); claude's own error text names this file and key as the way to trust a folder without sitting at the dialog, which is what makes the write a documented interface rather than a reach into private state. ADR-0021's rule that the engine never removes what the operator made is why the seed is add-only.

**Consequences**: a claude Ticket, verify candidate or Conversation on a herdr pool launches into a trusted worktree and never sees the dialog, so its readiness wait is spent on the TUI alone. `~/.claude.json` on a pool's machine accumulates one entry per pool worktree the engine ever launched claude into, which claude's own sessions there also do for every directory they visit. A seed lost to a concurrent rewrite, or one that could not land, surfaces as the dialog in the pane, which the launch answers by name or ends legibly (ADR-0016). Every Claude Code build that moves the dialog's words or its file is a one-line change in the dialog table or this seed, each of which names the build it was read from. Headless pools are untouched: `claude -p` skips the dialog itself. The test suite now starts every run with `CLAUDE_CONFIG_DIR` pointed at scratch (`bunfig.toml`, `engine/test-preload.ts`), because the first full run of this change seeded the operator's real file from seven Conversation tests; an engine that writes another tool's config needs its tests fenced from that tool's real files.
