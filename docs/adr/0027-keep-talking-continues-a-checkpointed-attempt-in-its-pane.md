# Keep talking continues a checkpointed Attempt in its pane

A Terminal-backed attempt that ends in a checkpoint leaves its TUI running (ADR-0016: the TUI stays alive after its Outcome), with the whole conversation that led to the checkpoint in it. Until now the Console dropped that pane the moment the Attempt ended: the Live attempt left the registry, so the card lost its Peek, its "Open in herdr" and its attach line while the Interrupt was still waiting, and the only answer was Resume, which launches a fresh Attempt in a new tab with a Brief and a Resume note for context. The agent that actually held the context sat idle beside it, and when the new Attempt was solo it shared the ticket's well-known Outcome and exit-code files with the old one (issue #139, https://github.com/BillyLuisNeedham/agents-console/issues/139). Very often the operator's answer to a checkpoint is a conversation, not a note: "yes, but" and "what about", with the agent that asked.

We decided that a checkpointed Attempt's pane stays the pool's while its checkpoint Interrupt waits, and that the operator can **Keep talking** to it. The pane is a **Held pane** (CONTEXT.md). The rule for which pane a checkpoint holds is that the checkpoint is about that pane's Attempt and its agent is still there to talk to: the checkpoint follows the Attempt's own ending (its `exited`, whatever raised it from there: the agent's own checkpoint, a lone verify attempt's flagged grade or blocked merge, a selected winner whose merge conflicted, a Continued attempt that could not be taught), no engine-raised checkpoint about the ticket's circumstances came after that ending (a branch held in another checkout says nothing about the agent in the pane), and the TUI has not exited (the wrapper runs in the pane's own shell, so a TUI that quit leaves a bare shell at its prompt, recognisable only by its exit-code file). The engine applies the rule where the checkpoint is raised and again from the latest `checkpoint` event after a restart, and shows the pane on the snapshot only while herdr lists it as it was recorded: under the recorded tab, in the Pool workspace (an enlisted pane in the operator's), and in the recorded directory, wherever the listing reports those. A herdr id is only an id, and a pane listed differently is not ours: never offered, never closed, never released, and left exactly as it is for the operator. The short pane and tab ids can be reused, so every `spawned` event also records herdr's `terminal_id` for the pane (the `tab.create` answer carries it on herdr 0.8.2, as every pane listing does, unique and never reused). Where both the record and the listing have one, it decides on its own: a match is ours even in a tab the operator has since moved to another workspace, and a mismatch is not ours whatever else agrees. An older record without it falls back to the tab, workspace and directory checks (the directory compared as herdr reports it, the physical path). Peek, focus and attach serve it exactly as they serve a Live attempt's pane, so ADR-0021's rule that the Console reaches only panes the engine registered still holds: a Held pane is the engine's record. An enlisted Ticket's pane is held too, while the Ticket still works in it: the agent there checkpointed, and nothing else watches the pane for the fresh Outcome the operator's talk leads to. Holding it takes nothing from the operator (ADR-0021 stands: nothing in this decision closes it, moves it, or touches its directory or branch), and it stops once the found work is dropped, when the pane went or an adoption let it go; a let-go is recorded as an event, so a restart does not take the pane back. A merge-conflict, merge-approval or selection Interrupt holds nothing, because none of them was raised by the Attempt whose pane it would be.

Keep talking starts a **Continued attempt**: a new Attempt, with its own number and its own Outcome, launched into the existing pane rather than a new tab. Reopening the ended Attempt so it could take a second Outcome was rejected: an Attempt ending is a recorded fact (the `exited` event, the Brief, the grade), and taking it back would make every reader of the events file ask which ending of an Attempt it is looking at. The Continued attempt's `spawned` event names the same pane and tab, `continued: true`, the Attempt it continues, the Attempt whose worktree and branch the work lives in, the Stream file the pane's `script` is still writing and where that file stood, so its log is its own part of the session and a restart can re-derive it.

It starts **at once**: not queued to the super-step boundary and not held by the Merge hold. That is an exception to ADR-0004, with Enlist (ADR-0021) as its precedent. ADR-0004 queues answers because processing mid-super-step races the join, spawns in the main checkout and merges; Keep talking does none of those. It launches nothing, opens no worktree, merges nothing, and changes one ticket that no super-step in flight is running. Its claim is synchronous (the checkpoint Interrupt answered, the marker in-progress, the next Attempt number, the `spawned` event, the Live attempt registered on the same pane), so no answer, boundary or second Keep talking lands halfway through it. What does need the boundary waits for it: the Continued attempt's ending is recorded off the drive the way an adopted attempt's is (merges chained onto the session merge chain), and a verify ticket's grading runs in the drive loop between super-steps; a grade still owed when the engine stops is rebuilt from the events at boot (a Continued spawn, then its done `exited`, with no `graded` after it) rather than lost to a fresh fan-out. A pool whose only unfinished work is a Continued attempt settles quiescent, not stalled, and keeps its store open for the ending.

**The pool checkout holds one agent at a time.** An Attempt that ran alone ran in the pool checkout, and continuing it puts an agent back there beside the drive. So Keep talking is refused when anything else writes in the pool checkout: a ticket the drive planned into it, counted from the plan, before its launch has spawned anything; a live or re-adopted Attempt; a live Conversation, enlisted ones and ones not yet re-adopted after a restart included; and the engine's own work landing there: a merge into it in flight, from its gate until it settles, a verify round deciding its merge, and a resolver working a merge that lands there, each named as the reason in the refusal. "In the pool checkout" is anywhere in its working tree, by git's own toplevel, so an enlisted agent in a subdirectory counts and a pool worktree does not. While a Continued attempt works there nothing new is planned into it (every other ticket gets a worktree) and nothing merges into it: the merge target is the checkout's own branch, the one the agent is committing on. Every merge into the checkout passes a gate inside its merge-chain link, at the moment it is about to touch the checkout; with no Continued attempt there the gate is not felt at all and the chain is exactly what it was. With one there, the link waits until the attempt ends, and so does everything chained behind it, the drive's own merge queue included: the pool waits behind the conversation in its checkout the way it already waits while a lone attempt works there. No deadlock is possible, because the Continued attempt ends outside the drive, on its own Outcome or its pane. A Conversation's End answers as soon as its ending is recorded and its tab closed, and its merge follows on the chain. A verify round's lone or selection merge is decided in the drive's grading, which waits at the same gate before it records any grade, so a shutdown while it waits leaves the grade owed rather than recorded and lost. A queued merge answer stays queued until the checkout is free. A ticket merge the gate holds is recorded `merge-deferred` the moment it is held, whether or not the drive is running, and the events that follow settle the record when the merge lands, conflicts or goes to a resolver. A shutdown releases every waiter and stops the drive there, and the next boot, once any Continued attempt is re-adopted, chains every unsettled deferred merge again through the ordinary merge path (and so through the gate), unless the ticket ran again since, where it lands or goes to the resolver machinery like any merge, never left standing in the Merge queue with nothing moving it; a dropped Conversation End is finished at the next boot. Once an enlist has captured the merge target, merges land in the engine's own merge checkout instead, and nothing waits.

The engine types **one teaching Turn** (`buildContinuedTeaching`), once the pane's Turn state is waiting and never mid-reply, bounded as an enlist's is, and then leaves the pane to the operator. The agent already wrote the Outcome it was asked for and believes its part is over, so the Turn says the operator chose to carry on here, that the old Outcome is spent, and restates the whole Outcome contract with the exact path; the checkpoint's Outcome file is removed before the watch is armed so it can never be read as the new one. A pane that will not take the Turn ends the Continued attempt at once as a checkpoint of the engine's own saying so, still over the same pane, rather than leaving a ticket running on an agent that does not know it owes an Outcome. The ending is a valid Outcome on disk raced against the two ways the agent can be gone without one: the wrapper's exit-code file landing (the TUI exited while its pane, a shell, stayed open) and the pane leaving herdr's listing. The exit-code file is the one the pane's wrapper writes, the checkpointed chain's first attempt's; one older than the checkpointed Attempt is stale and cleared at the claim, and one newer means the TUI already exited, which is no Held pane at all, so from the claim on its landing can only be this TUI exiting. A valid Outcome wins whichever observation came first, so an agent that writes its Outcome as the operator closes the tab has finished, not crashed. Outcome done ends the ticket as any done does (the merge chain on a solo ticket, grading on a verify one); Outcome checkpoint raises a fresh Interrupt with the new Brief over the same pane, which can itself be continued; a TUI exited or a pane gone with no Outcome is a crash, as it is for any terminal attempt. An enlisted Ticket's Continued attempt ends by the enlisted rules instead, recorded by the same code its enlisted attempt was and raced the enlisted way (an enlisted pane has no wrapper and no exit-code file): done merges the found branch in place, a pane gone first is a checkpoint that keeps the branch, and its Assignment stays as found.

The Continued attempt runs under **the pane's Assignment**, the checkpointed Attempt's own as its `spawned` event recorded it (every `spawned` event now carries the harness and model it launched with), whatever a Reassign has written since, because that is the agent in the pane. It is frozen across a config reload while it runs, like an adopted or enlisted attempt's, and the ticket goes back to the config's Assignment at its ending. On a `verify: N` ticket the Continued attempt runs alone and is **graded as a lone attempt**, verify: 1 semantics whatever N is: there is one agent in one pane, nothing to fan out or select between. A flagged grade becomes a checkpoint Interrupt over the same pane, so it too can be continued; a pass merges the branch the chain has been working on. Its files are attempt-numbered as the Attempt it continues was, and grading follows it back to that Attempt's worktree and branch. A Continued attempt still live when the engine stops is re-adopted at boot like any Terminal-backed orphan, adoption interrupt included, with its own runtime and no second teaching Turn; answering the adoption interrupt abandons it and closes the pane, as for any adopted attempt.

**Plain Resume closes the old pane.** When a ticket's fresh Attempt launches after its checkpoint was answered with Resume, the engine first closes the tab of the checkpointed Attempt, so two agents never share the worktree and a solo ticket's well-known Outcome and exit-code files. The tab is the one the Attempt named by the ticket's latest `checkpoint` event ran in (on a verify fan-out, the checkpointed candidate's), and the close happens once: it is recorded as a `tab-closed` event, so a later Resume, after a crashed re-run say, never reaches back for it, and a headless fallback, which recorded no tab, closes nothing. A tab a later Attempt ran in after that checkpoint (a Continued attempt that then crashed) is that Attempt's now and stays open, as a crashed attempt's does. It is derived from the events, so a Resume answered before a restart still closes its tab after it. It closes only what is certainly the pool's and idle: never a tab over a pane that is live, held, registered or anyone's enlisted, and never one herdr lists differently from how it was recorded; a listing that could not be had closes nothing. This narrows the "deliberately left open" clause of ADR-0014's close-on-role-end amendment for checkpoints only: a crashed attempt's tab still stays open.

Tabs otherwise **close only on the operator's word**. A crashed attempt's tab, a done ticket's tab waiting on its merge or run in a pool with nothing to merge, and every other tab the pool opened over an Attempt or Conversation that has ended accumulate in herdr's tab bar, and so does a started Conversation's tab after a Stop or Restart, which the next boot marks crashed without a word to herdr. These are **Finished terminals** (CONTEXT.md), derived and never recorded: the tabs every `spawned` event names, less the ones herdr no longer lists, less any tab herdr lists differently from how it was recorded, less any tab over a pane still in use (a Live attempt's, a Held pane, a live Conversation's, one the engine counts as registered) or named by any enlisted Ticket's or Conversation's events. That last is not only an enlisted owner's own tab: an operator can enlist the still-live agent in a finished tab of the pool's own, and from then on that tab is theirs (ADR-0021), whoever opened it. The pool header offers "Close N finished terminals" behind the same inline confirm Stop uses, and the engine closes the set it derives afresh at that moment. Every close the engine makes by rule stays best-effort, but none is silent any more: a tab herdr refuses to close lands as a `tab-close-failed` event on its owner's log and a pool log line naming the error, where a swallowed catch used to hide why a tab stayed open. Every close that lands is recorded as a `tab-closed` event (matched by terminal id where one was recorded), so the next closer of the same tab (a Conversation's End and its ending's sweep, a Resume or bulk close and a later merge) does not ask herdr again, and a tab herdr answers `tab_not_found` for is closed already, not a failure. A live Conversation's pane and tab are untouchable too, whether or not the engine has re-adopted it yet (ADR-0018's issue #140 amendment). Closing Finished terminals automatically, at a pool's done or on a timer, was rejected: a finished terminal is often exactly what the operator wants to read next (the crash, the last thing the agent said), and nothing is lost by leaving it open.

Whether a Held pane or a finished tab is still there is the **pane survey**'s to say: one daemon-wide `pane.list`, cached, on a slow cadence (15 s) and on demand whenever the engine holds a pane, continues one, or closes the finished set. A caller that has just changed something is answered by a listing that began after its call, never one already in flight, and an answer herdr gives without a panes list leaves the last good listing standing rather than reading as every pane gone. The snapshot reads the cache and never herdr, and a listing emits only when what the snapshot derives from it moved, because the snapshot is emitted far more often than panes come and go.

**Consequences**: a checkpoint no longer ends the engine's interest in a pane, so the Console's pane surfaces key off "the ticket's pane" (a Live attempt's or a Held one) rather than the Live attempt alone, and a Held pane is also one the enlist picker refuses. The ticket log gains Attempts with no Stream file of their own, whose log is a slice of the Attempt before's typescript. The survey is a new, bounded herdr cost of one listing per cadence per pool. Held panes are not persisted; a restart finds them again from the events and the survey. Keep talking is offered only where a pane exists, so a headless pool never sees it.
