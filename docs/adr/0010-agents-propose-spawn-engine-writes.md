# Agents propose Spawn tickets; the engine writes the pool

A ticket attempt often discovers more work than its own ticket covers: a follow-up fix, a piece of scope the Spec missed, a refactoring the diff revealed. Today that discovery dies in the attempt's notes, because the agent's contract lets it write exactly one thing — its Outcome — and the pool's ticket set is fixed at `startPool`. Billy could hand-write the follow-up into `issues/` and hope an interrupt answer re-scans the pool, but that requires him to be watching, and the server wouldn't render the new card until restart anyway. This was issue #32 (https://github.com/BillyLuisNeedham/agents-console/issues/32); the design is `docs/specs/2026-09-03-spawn-tickets.md`.

We decided the attempt proposes follow-up tickets in its Outcome JSON (a new optional `spawn` array of `{ title, body, blockedBy }`), and the engine writes those tickets into the pool itself at the super-step boundary, exactly as it already writes grader and head-to-head tickets. The agent never picks ids (the engine assigns `<parent-id>-spawn-N`), never writes ticket files, and never touches the pool directory. Spawned tickets are ordinary tickets from the moment the engine writes them: they schedule, assign, verify, and render like any other, and they may themselves spawn, bounded by the caps.

Four alternatives were weighed. Letting agents write `issues/*.md` files directly breaks the standing rule that agents never write protocol state (ADR-0005): a torn write or duplicate id at re-scan time throws inside answer processing and can silently swallow a queued human answer, and worktree-seeded copies of the issues directory make "which copy did you write?" a whole new failure class. A blocking approval interrupt for every proposal (the Brief proposes, the human approves, processing writes) hands each decision to a human who is often not the point of running a pool unattended, and pauses the run on every discovery. A `POST /api/tickets` server endpoint gives the human a creation affordance but leaves running harnesses without a callback path, and shares the server-staleness work with every other option anyway. Doing nothing and relying on manual file edits plus interrupt-time re-scan (the accidental mechanism that exists today) leaves the feature invisible in the UI and dependent on an interrupt happening to arrive.

The propose-via-Outcome shape was chosen because it deletes the bad-write class rather than validating around it: the only writer of pool state remains the engine, proposals that fail validation (unknown `blockedBy` id, thin body, over-cap) are dropped with a ticket-log entry rather than failing the attempt, and the whole mechanism rides the adoption seam the engine already proved with grader tickets. The cost is real: the Outcome schema grows, the engine must re-scan and adopt at every super-step boundary rather than only at answer processing, and the server must refresh its pool metadata per snapshot so spawned cards render live — work every option shared except "do nothing".

**Consequences**: caps exist and are engine-enforced (default 5 proposals honored per attempt, 20 per run; overflow is truncated and logged, never an error). Spawned ids live in a visible `-spawn-N` namespace so provenance is obvious on the canvas, and that namespace — like `-grader-N` — is reserved. Validation is per-proposal, never per-attempt: a good attempt with a sloppy proposal keeps its result. `blockedBy` may only name ids currently in the pool (in-flight included — the ticket simply waits), which keeps the hermetic-pool rule enforced by the same mechanism as typos today. Grader and head-to-head tickets cannot spawn. The server's load-meta-once behaviour is replaced by a per-snapshot refresh, which also fixes the standing bug that grader tickets never rendered as cards until restart.

**Amended by ADR-0029 (issue #149)**: the caps are no longer engine constants. They are Pool settings (`spawnCaps`, defaulting to 5 and 20), reloaded at the boundary, and a run is one Console boot. Overflow is no longer truncated: a proposal beyond either cap is held for the operator to adopt or discard. A proposal may also `block` named tickets, or every ticket not yet started.

**Amended by ADR-0029's issue #150 addendum**: a proposal no longer waits in an in-memory buffer for the boundary. It is taken as soon as its Outcome is read, checked, and kept on disk as a Pending spawn (within the caps) or a Held spawn (beyond them, marked `overlaps`, or held by the operator) until it lands. Agents read the pool's Spawn ledger before proposing.

**Amendment (2026-10-03, issue #116)**: a proposal may carry an Assignment request, `assign` with harness, model, effort and drivers, never `verify`, which stays the operator's call and is ignored with a log line. The request is persisted on the child's line-1 marker as `spawn-assign`, so a reload or a restart resolves it the same way, and it ranks field by field under the operator's `console.json` `assign` entry for the child and over the parent's Assignment.
