# Attempts may run terminal-backed in herdr panes

A pool may set `terminal: herdr` so every spawn site — implement, resolver, grader, head-to-head — runs its attempt in a herdr pane (created via herdr's socket API in the attempt's worktree cwd, always `focus: false`) instead of a headless `Bun.spawn`. This is the engine half of the North Star (issue #29): every running agent is a real terminal the operator can watch and type into, while the engine stays oblivious to that input — an attempt still ends only on exit plus Outcome. Because herdr's API exposes no exit codes and bounds scrollback, the pane command is a wrapper shell string — `harness … 2>&1 | tee <stream-file>; echo ${PIPESTATUS[0]} > <exit-code file>` (bash, for `PIPESTATUS`) — writing the same files `spawnToLog` writes today. The engine waits on herdr's `pane_exited` event plus the exit-code file, and derives the live log by tailing the tee'd stream file with a follow-file reader feeding the existing streamlog derivation (ADR-0012). Files remain the source of truth; the pane is purely a viewport and input path. The `spawned` event records the `pane_id`; on boot the engine reconciles against herdr's snapshot — live panes are re-adopted, missing ones crash the attempt. Exited panes persist until their ticket merges, then the engine closes them. Herdr is optional: absent daemon or protocol mismatch falls the pool back to headless with a visible warning; it becomes the default once proven.

**Considered options**: building the Console's own PTY layer (node-pty + xterm.js) was rejected — herdr already solved PTY, scrollback, agent-state detection, and attach. Reconstructing logs from `pane.read` polling was rejected — worse fidelity than the tee'd files, and it would rewrite the ticket-log pipeline. Implement-only terminal backing was rejected — all spawn sites share one code path, and the North Star says *every* agent.

**Consequences**: if the herdr daemon dies, every pane dies with it — all in-flight attempts crash simultaneously and raise crash interrupts; accepted as no worse than the host rebooting today. The engine gains a second wait-path (event + file instead of child exit) and a follow-file tailer, but the log/Stream/Outcome contracts are untouched. The UI surface — open-in-herdr button vs embedded terminal — is deliberately deferred pending a prototype.

**Amendment (ADR-0015)**: the attempt-terminal unit is a named tab per attempt, not a bare pane: `tab.create` with label `<ticket-id> · <ticket-title>` (capped at 40 chars), `focus: false`, in the attempt's worktree cwd; the pane id is recovered via `pane.list` by tab id because `tab.create` returns none, and is recorded on the attempt's `spawned` event as `pane_id` (superseded on both counts by ADR-0015's issue #94 amendment: the tab names the Pool workspace, and the pane id comes off the `tab.create` answer's `root_pane`).

**Amendment (ticket 01-spawn-1-spawn-1)**: two refinements to the close lifecycle and the daemon-death story above. First, "exited panes persist until merge, then the engine closes them" only ever fires for attempts whose ticket merges; grader, head-to-head, and losing verify-candidate tickets never merge, so their tabs would accumulate in the operator's tab bar across verify fan-outs. The close rule is now: a tab closes the moment its attempt's role ends. For merging attempts that is the merge; for grader tabs the grade landing (or the grader's recorded failure); for the head-to-head tab the judge's verdict; for losing candidates the selection's loser discard. All closes stay best-effort and keyed off the tab id on the attempt's `spawned` event. Deliberately left open: a flagged lone attempt's tab (verify:1 checkpoint; the human may want to inspect the terminal before deciding) and crashed ordinary attempts. Second, daemon death no longer crashes every in-flight attempt at once: when the pane-end subscription is lost (socket error or close, e.g. a daemon restart) the pane wait settles as "lost" and the engine falls back to an unbounded poll of the wrapper's exit-code file, unbounded the way the headless spawn's wait on its child is unbounded. The attempts ride out the outage instead of raising crash interrupts in unison; if the daemon's death killed the pane's harness, recovery is the operator's, since nothing will write the exit-code file.

**Superseded in part (by "endings are raced" below)**: the second half of the amendment above, the pane-end subscription as the primary ending with the exit-code file polled only once the subscription reports itself lost, no longer describes how an attempt ends. It is left exactly as written because it was a decision made, shipped and run on a real pool, and what it missed is only visible from there: it settles the wait on a subscription that *reports* its own failure, and a subscription can simply stop delivering without erroring, closing or hanging up. The first half, the close-on-role-end rule, is untouched and still in force, as are the two amendments that follow it, the `bash -c` wrapper and `EXIT_CODE_UNREADABLE`.

**Amendment (live on a zsh host)**: the wrapper's premise that "the pane's shell is bash (herdr spawns bash panes)" is false — herdr spawns the operator's login shell. On a zsh host `${PIPESTATUS[0]}` expands to nothing (zsh spells the array `pipestatus`), so the exit-code file received a bare newline, `readExitCode` fell through to its `return 1`, and every attempt that succeeded was reported as `harness exited 1` and raised a crash interrupt — verified on a real queue, where the attempt's own Outcome said `done` with a commit and its tests passed. The pipeline is now wrapped in an explicit `bash -c`, with the trailing `exit` left outside it because it is the pane's own shell that must end for `pane_exited` to fire. `PIPESTATUS` remains the mechanism: it is the one portable way to read a pipeline's first status, so the fix guarantees the shell it needs rather than guessing at the host's.

**Amendment (an unread exit code says so)**: the zsh bug above cost a day of misdirected reading because `readExitCode`'s failure translated a missing or unparseable file into `1`, which is indistinguishable from a harness that really exited 1 — the logs blamed the harness for an exit it had never made. An unread code is now its own value, `EXIT_CODE_UNREADABLE`, safe as `-1` because a shell status is 0-255 and cannot collide with it. Every spawn site still crashes the attempt on it, unchanged; what changes is the reason, which names the unwritten exit-code file and the pane wrapper instead of the harness. The rule that a non-zero exit crashes an attempt *even when its Outcome file claims success* is deliberately untouched: the Outcome is the agent's account of itself, the exit code is evidence, and an agent that writes a cheerful Outcome and then dies is exactly what that rule exists to catch.

**Amendment (endings are raced)**: the ending design marked superseded above, the second amendment's fall back to polling the exit-code file once the subscription reported itself lost, was run on a real pool and found to have a silent hole. An attempt finished, the wrapper wrote `0` to its exit-code file, and the engine never noticed: the pane-end subscription had stopped delivering while the socket stayed open, so nothing settled the wait and nothing went looking at the file, because the file was gated behind the subscription admitting it was lost. The Console showed `running / idle 98m` over work that was done and committed. Duration was the exposure, and shorter attempts kept finishing, which is why it survived so long. An attempt ending is now whichever of two independent observations arrives first, raced, with neither trusted alone: the pane's end as reported by herdr, and the appearance of the exit-code file the wrapper writes before its shell exits. Ranking them was rejected in both directions, because either ranking reinstates a single point of failure. Subscription-primary is the design that parked: it gates the one observation that does not need the daemon behind the one that does. File-primary parks on precisely the case the pane event exists to catch, since an operator who closes a tab, or a pane the host kills, produces a pane end and no file ever. Raced, each covers the other's blind spot. For the case where both fail at once, the subscription gone quiet *and* the pane dead without a final write, the wait re-checks the pane listing on a slow cadence throughout (every 30 seconds, invisible against attempt durations measured in minutes and one cheap request each); a pane missing from the listing is given a short grace window (10 seconds) for the file to land, covering the ordering the exit-code read already assumes, where the daemon reaps the pane just ahead of the wrapper's last write, and a pane still gone with no file after it is a genuine crash and is reported as one, naming the pane and the unwritten file. There is deliberately no wall-clock deadline on an attempt: a ceiling generous enough for a legitimate 98-minute review is too generous to catch anything, and one tight enough to catch something kills real work. Liveness, not duration, is the signal. `EXIT_CODE_UNREADABLE` from the amendment above stays load-bearing, since the raced ending still reads the code the wrapper writes.

**Amendment (one Attempt-run module is the shared code path)**: "all spawn sites share one code path" above was true of the wrapper and the wait, and false of everything around them: the four engine sites each re-implemented naming, rotation, the `SpawnContext`, the terminal decision, the tab open, the argv choice, the result read and the crash reason, and Conversation start was a fifth copy that opened its tab and sent its wrapper by hand, so it never gained the readiness wait or the launch-failure endings the tickets had. The shared path is now the Attempt-run module (`engine/attempt-run.ts`), and it is split in two on purpose: `launch` takes an Attempt from a stale result file to a live pane or headless child with its `spawned` event recorded and its prompt delivered, and `await` takes a launched Attempt to its ending, result and crash reason. Ticket, resolver, grader and judge run both halves; a Conversation runs `launch` only, because nothing waits on a Conversation but the operator. Two things are deliberately not shared, because each role's rule differs and the difference is the role: the marker status write (ADR-0005) and the tab close (the close-on-role-end rule above). A Conversation gets no headless fallback: ADR-0018 makes it terminal-backed by definition, and a Conversation with no pane has nobody to talk to, so a failed tab or wrapper send is a start failure, not a fallback.

**Amendment (issue #161, ADR-0032)**: the card's terminal peek is no longer polled by each tab every 2 s. The server reads every terminal-backed pane once per 2 s check, for all tabs together. It uses the same read as `/api/terminal/peek` (the engine's recorded read first, otherwise a visible-viewport read) and pushes only the peeks whose text changed, to visible tabs only. A pane that just appeared is read at once. "Open in herdr" is a `terminal.focus` request on the same socket. The pane is still only a viewport and an input path.
