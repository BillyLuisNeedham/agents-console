# Hold the whole super-step while any done ticket is unmerged

A ticket's marker is written `done` at attempt exit (`engine/engine.ts:3917-3947`), before its `pool/NN` branch merges to main. The ready set (`readyTickets`, `engine/engine.ts:283-299`) unblocks downstream tickets on that marker alone, so a dependent ticket could spawn against a main that did not yet contain its blocker's work — ticket 15 spawned while ticket 10 sat behind a merge conflict. This was issue #41 (https://github.com/BillyLuisNeedham/agents-console/issues/41).

We decided the scheduler computes no ready set at all while any ticket is done-but-unmerged: the whole pool pauses for merge hygiene, so every ticket in the next super-step starts from a main that contains all finished work. The hold engages whenever a ticket has `marker=done` and its `pool/NN` branch is not in its merge target, regardless of whether that target is main or a feature branch, and it applies everywhere the ready set is computed — the main scheduling loop, verify flows, and selection runs alike, one rule on one code path.

The hold lifts in exactly two ways: a merge lands (the operator approves the existing merge-approval interrupt, or merges manually from the CLI — the next ready-set computation simply sees it landed), or the merge is rejected, which reopens the ticket so it no longer counts as done. Tickets already running when the hold engages finish undisturbed; the hold gates only spawning. No new persisted state records the hold — it is derived on demand, including at startup, by scanning markers for done tickets whose branches are unmerged, consistent with ADR-0007's derive-server-side pattern. No new "held" interrupt is raised either: the existing merge-approval interrupt is the signal and the action, while the Console card shows a "done, merge pending" label (via `EnrichedTicketState`, `engine/server.ts:110-129`) so a held pool shows why it is held.

**The pause is a wait, not a quiesce.** A held pool's drive loop stays alive: it polls the derivation on a short cadence, drains queued answers as it waits, and computes the ready set fresh the moment the hold lifts. Quiescing instead would strand a manual CLI merge behind a drive that already exited, contradicting story 6 (unstick the pool without touching the Console), and would strand an approval the same way. The phase stays `running` while held; the pool settles only after the hold clears, so the existing quiescent/done/stalled semantics are untouched.

**The hold outranks the engine-id pass-through.** The check sits first in `readySet`, before ticket 01's clearing of engine-run proposals, so a verify round's graders and the selection run's head-to-head judge are withheld exactly like ordinary tickets. A withheld round waits the hold out through the same drain-and-poll helper and then recomputes; an all-engine proposal returns empty for no reason but the hold. Draining mid-fan-out is safe precisely where the boundary drain is safe (ADR-0004): at every wait site every attempt has exited and the super-step join is done, so no answer can be undone and no in-flight spawn can race a merge, and without the drain the pause would deadlock against the very approval that lifts it, since queued answers otherwise process only at the boundary the paused fan-out never reaches.

**Rejecting a merge reopens the ticket.** The merge-approval interrupt's reject now discards the resolver's staged resolution and sends the ticket's marker back to ready, instead of the old conversion to a manual-resolution interrupt with the ticket still done. Reopening is what lifts the hold; the parked branch is reused by the re-run, the way a review-reject re-run reuses one, and the rejection note rides along as a durable resume note. The by-hand path stays on the merge-conflict interrupt: resolve in the checkout and resume, or merge from the CLI and let the derivation observe it.

Alternatives weighed: gating per-ticket (unblock a dependent only when its specific blocker is merged) is finer-grained but keeps two facts the scheduler must join per ticket and leaves a partially-unmerged pool scheduling new work; holding was chosen for simplicity and for the stronger invariant that a super-step always sees fully-merged main. Draining pending approvals before computing the ready set narrows the window but loses the race whenever the operator is slow, so it cannot be the mechanism. Keeping per-ticket gating plus the hold was rejected as redundant once the hold exists.

The outcome channel is unchanged: a blocker's Outcome JSON still carries its result downstream, only the timing changes: downstream tickets now wait for the merge as well as the marker. The pinned test that asserted a downstream ticket receives its outcome even when the merge conflicted is rewritten ("holds a downstream ticket until its blocker's conflicted merge lands, then passes the outcome through", `engine/engine.test.ts`) to assert the downstream ticket waits.

The card label is one server-side derivation of the same fact, read through the enrichment seam: a ticket whose snapshot status is `done` and whose `pool/NN` branch has not landed in the merge target carries `mergePending` on `EnrichedTicketState`, and every UI surface renders it as "done, merge pending" without probing git itself. The merge target is the pool checkout's current branch at derive time, so a feature-branch target holds the label main would clear. A missing branch reads as landed, the same reading `mergeBranch` applies: the engine deletes the branch once its merge lands, and a ticket that ran in the main checkout never had one. Because the fact is derived on demand, it is re-derived at serve time too: a manual CLI merge while the pool sits quiescent raises no snapshot, so `/api/state` and a stream connect re-derive before serving, and a Console opened after such a merge sees the label gone.

**Consequences**: "done" no longer means "downstream may start"; it means "work finished, merge pending or landed". The spawn-time warning about unmerged blockers was expected to become dead code and be removed, but no such warning exists anywhere in the codebase, past or present: there was nothing to remove, and no code path contradicts the hold. A stuck merge now stalls the entire pool, not just dependents, deliberate: the operator's merge queue is the bottleneck the hold makes visible, and the escape hatches (approve, reject, manual merge) are the controls that already exist.
