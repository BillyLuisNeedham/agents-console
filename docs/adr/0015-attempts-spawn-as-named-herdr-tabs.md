# Attempts spawn as named herdr tabs, not anonymous panes

ADR-0014 settled that a `terminal: herdr` pool runs every attempt in a herdr pane created via the socket API, always unfocused. Prototyping the Console surface (issue #29, `prototype/console-terminal-surface/`) refined that: the attempt-terminal unit is a whole named **tab**, not a bare pane. Each spawn site (implement, merge resolver, verify grader, head-to-head judge) opens its own tab via `tab.create` with `label` = `<ticket-id> · <ticket-title>` (capped at 40 characters), `focus: false`, and `cwd` = the attempt's worktree, so the operator's tab bar reads as the roster of tickets in flight and a spawning ticket never steals terminal focus. `tab.create` returns no root pane id (verified herdr behaviour), so the engine recovers the pane id from `pane.list` filtered by the created tab's id and records it on the attempt's `spawned` event as `pane_id`; the Console's peek/focus endpoints (issue #29) key off that recorded id. Herdr stays optional exactly as ADR-0014 promised: a daemon that is absent or misbehaving never blocks the spawn; the attempt falls back to headless for that run and the spawned event carries `pane_id: null` plus a `terminal_error` fact, so the fallback is visible on the ticket log. What executes inside the tab (the wrapper-shell run, `pane_exited` wait, reconciliation) remains ADR-0014's engine work, unchanged by this refinement.

**Considered options**: naming the tab after the ticket was the point of the feature, and the ticket title (the Issue file's first heading) is the only human-readable name the engine already has; no separate display-name field was added. `pane.split` was rejected for creation because it ignores `cwd` for workspace placement (verified prototype finding) and produces anonymous splits, which is the problem this refines away. A generated monotonically increasing label was rejected: the mapping from tab to ticket must be obvious without memorising ids, and the spec's user stories demand `<ticket-id> · <ticket-title>` verbatim.

**Verified herdr quirks (live against herdr 0.8.2, prototype)**: three behaviours the prototype confirmed by observation and the implementation must not rediscover by debugging. (1) `pane.read`'s `revision` does not advance reliably — verified stagnant at 0 while output grew — so freshness never comes from the revision counter; a caller re-polls and diffs the returned text. (2) A literal `\r` inside `pane.send_input` text is pasted data, not a submit (bracketed-paste semantics, verified); submission requires the command line as printable text plus `keys: ["Enter"]`. (3) Reads against a background (unfocused) tab return empty for the first seconds after `tab.create` because herdr warms up viewports lazily (verified); an empty read means "waiting for output" and must be treated as such, never as an error. Two more, verified against herdr 0.8.2 while fixing issue #61: (4) a closed tab takes its panes silently: `tab.close` pushes one `tab_closed` (carrying `tab_id`, no pane id) and no `pane_closed` for any pane in the tab, whereas `pane.close` does push `pane_closed`, and a shell that exits pushes `pane_exited` and then its tab goes with no further event; a wait on a pane's end must therefore also subscribe to `tab.closed` and re-check `pane.list` when one lands, which is safe because the listing drops the panes before `tab.close` is answered and the `tab_closed` push trails that answer by tens of milliseconds (verified six of six closes). (5) `events.subscribe` replays retained history before live events: a fresh subscriber first receives the daemon's backlog of past events, paced at about one per 100ms, so a subscriber must filter by id and treat a replayed end for its own pane as the real end it missed.
