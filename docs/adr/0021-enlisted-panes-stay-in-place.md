# An enlisted herdr pane stays in place, and the engine never closes, removes or deletes what the operator made

Billy opens a claude or opencode terminal in herdr by hand, in the pool's repository, and talks to the agent for a while before it is clear the work matters to the pool (issue #101, https://github.com/BillyLuisNeedham/agents-console/issues/101). The engine only knew panes it had opened itself, so that work either stayed outside the pool, invisible on the canvas and unmergeable through it, or the context was re-typed into a New Conversation and the terminal abandoned. Enlist is the operator's action that makes a live pane a Pool citizen, as a Ticket or a Conversation, chosen at that moment and fixed from then on.

We decided the pane stays **in place**. The alternative was re-homing (the prototype's variant C): relaunch the harness with the session id herdr reports, in a fresh pool worktree, so that from the first moment an enlisted attempt is indistinguishable from one the engine launched. It was rejected because a session id restores the transcript, not the terminal. The uncommitted edits, the files open in the editor beside it, the scrollback, and every commit already made on the branch live in the checkout and the pane, not in the harness's session record, and those are exactly what makes the pane worth enlisting. Re-homing would ask the operator to trade the working state for a copy of the conversation about it. So the pane id, the harness, the harness session id, the directory and the branch are recorded as found. The Assignment is recorded as found too: the harness is known, the model is not, because herdr does not report one, and the card reads "as found" where the model would be. The one thing the engine changes is the branch, and only when it must: a pane sitting on the merge target gets `pool/<pool>/<id>` created at its HEAD and checked out in place, which at the same commit carries the uncommitted changes with it; a pane on any other branch keeps that branch as the ticket's own. Which of the two happened is recorded on the ticket log.

Because the pane is the operator's, **the engine never closes it, never removes its directory and never deletes its branch**, at merge, at ending, at End, or at any other time. Those two behaviours, closing the attempt's tab and removing the worktree after a merge, belong to pool worktrees only, and both call sites now skip work the engine did not create. What the engine does instead is record: a pane found gone after the Outcome is a trailing exit, a pool log line and nothing on the ticket, so tidying tabs never fails a finished ticket; a pane found gone before the Outcome lands the ticket in a checkpoint saying the pane went and the branch is kept, and the operator decides what happens next rather than the engine re-running blind over a checkout it does not understand; an enlisted Conversation whose pane goes is crashed with its branch kept, as ADR-0018 already has it for a spawned one.

The guarantee behind peek and "Open in herdr" changes shape to allow this. It read as spawned-only: a pane the Console could reach had to be one the engine had opened. That was a proxy for the rule that actually matters, which is that the Console may only reach panes the pool owns, and it would have shut an enlisted pane out of the two routes that make a card watchable. The guarantee is now **engine-registered**: peek and focus resolve a pane from the snapshot's live attempt or Conversation view, exactly as before, and an enlisted pane is in that view because registering one mirrors boot re-adoption. An enlisted pane is therefore as reachable as a spawned one and no more reachable than that, and a pane nobody enlisted is still unreachable.

Three further alternatives were passed over: self-enlist typed from inside the terminal (variant D) and a drag-from-a-tray gesture (variant E), both rejected for one Console entry point; and converting an enlisted Ticket to a Conversation or back afterwards, rejected because the two differ in whether they have an end, which is not a property worth changing under running work. The prototype's throwaway branch `prototype/enlist-herdr-terminal` holds the five variants and remains the primary record of why F was chosen.

**Consequences**: `enlist-N` is a reserved id namespace, enforced on markers by requiring an `enlisted-from=<paneId>` field, so a hand-written ticket cannot claim one. The session keeps an `enlistedWork` map from an enlisted id to its found branch and directory, seeded at enlist and rebuilt at boot from the `spawned` event, because the merge hold and the merge paths can no longer derive a branch as `pool/<pool>/<id>`. There is no wrapper around an enlisted attempt, so there is no exit-code file and no Stream file: the ending is raced between a valid Outcome on disk and the pane leaving herdr's listing, the ticket log holds lifecycle events only, and Vitals read the found directory's diff. `verify: N` on an enlisted Ticket has nothing to run N of and is ignored, logged once at enlist. Enlisting a pane that sits in the pool's own checkout captures the branch it was found on as the pool's merge target and hands that checkout to the operator for the rest of the pool's life: from then on the engine merges in a short-lived linked worktree of its own on the target and gives every ticket a worktree, so no merge and no attempt ever checks out another branch in, or writes into, the checkout a live enlisted agent works in (an earlier cut checked the target out in place before each merge, which yanked the agent onto the target mid-work). Git allows a branch in one worktree at a time, so a pane on the merge target is necessarily in the pool's own checkout; refusing that case would have removed enlisting from the merge target altogether, which is why the merge moved instead. A restart re-adopts a live enlisted pane with its runtime, so the sidebar keeps following its Turn state; answering the adoption interrupt lets the pane go, never closes it, and re-runs the ticket as an ordinary attempt with a real Assignment in a pool worktree; when the enlist had created the pool branch in that checkout, the re-run waits as a checkpoint until the checkout is off the branch, because git allows a branch in one worktree at a time. A Conversation's merge goes through the same merge checkout, and the captured target is restored at boot from either arm's enlist record. An enlist gives a working pane the same bound a Launch gives a TUI to reach its ready frame; the teaching Turn is typed the moment the agent is waiting on the operator, and a pane still working past the bound is refused with nothing left behind, never a Ticket whose agent was not taught. The enlisted tab stays in whatever herdr workspace the operator had it in and is never moved into the Pool workspace.

**Amendment (issue #122, the engine reads only what the operator sees)**: "the engine never closes it, never removes its directory and never deletes its branch" was not enough to keep the pane the operator's. Watching an enlisted pane for Turn state read herdr's `recent` source, two hundred lines of scrollback every two seconds, and the Console's card Peek read another eighty lines of it on its own two-second poll, so one pane was read twice per tick, and on a Mac each scrollback read moved the viewport up and back under the operator's hands (issue #122, https://github.com/BillyLuisNeedham/agents-console/issues/122); stopping the Console server stopped it. Both reads are now one: the steady-state watch of a pane an operator sits in, enlisted attempts and Conversations alike, reads the `visible` source, the viewport and nothing above it, which is all Turn state ever needed, and it records that read so the Peek route serves it without a second call to herdr. A spawned terminal-backed attempt, which no loop watches, is the one pane the Peek route still reads live, and that read is `visible` too. Launch-time reads (readiness and echo polling on a tab the engine opened and nobody is typing in) keep their two-hundred-line `recent` read: a fresh pane's viewport is mostly blank above its prompt, the prototype found small reads of it come back empty, and the operator is not in that pane. The echo check that confirms a Turn the engine typed (the teaching Turn, a Notice) is the one scrollback read an enlisted pane still gets, a few reads over the seconds the typing takes, never a steady tick; left as it is because it shares the launch path, and a follow-up may move it to `visible` once the Mac confirms the fix. The alternative, slowing the polls, was rejected because a slower jolt is still a jolt. Confirmed on a Linux host that a `visible` read leaves herdr's reported scroll offset untouched; the Mac is the host the fix is for, and it is verified there after merge.
