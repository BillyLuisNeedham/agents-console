# A model name belongs to one harness, and the resolver fails at boot without one

The Assignment resolved harness, model and effort field by field, each from the first layer that set it (ADR-0013, ADR-0018), and the resolver fell back the same way to `defaults.model` and then the Machine defaults' model. Nothing checked that a model came from a layer set for the same harness. A mixed-harness pool, with defaults on cursor `auto` and the resolver on claude, launched `claude --model auto`. Claude Code rejected it, every merge conflict fell to the manual path, and the failure showed only in `runs/NN.resolver.log` (issue #37, https://github.com/BillyLuisNeedham/agents-console/issues/37). An assign entry that set only `harness` had the same bug. ADR-0028 already said a model name and an effort word belong to one harness. This ADR makes the engine act on it.

**A layer's model and effort are owned by a harness, the Owning harness (CONTEXT.md).** It is the harness that layer sets, or, when it sets none, the harness of the nearest lower layer that does. The Machine defaults' own harness owns their model and effort. The legacy `~/.issue-runner` behind them fills their harness and model as one pair: its model never fills in beside a harness the JSON file names other than its own, and its harness never fills in beside a model other than its own. A resolved harness takes a model or effort only from a layer it owns. A layer owned by another harness is skipped and the search continues down the chain. When nothing is found the field is unset. So `defaults { cursor, auto }` with `assign.t { "harness": "claude" }` gives `t` claude with no model. A model set above a harness switch still pairs with it: `{ "model": "opus" }` on the entry above `{ "harness": "claude" }` on a lower layer gives `claude opus`. Same-harness inheritance is unchanged. A hand-written null harness resolves to no harness, which owns no model, so it takes none from the layers below. The rule lives once in the core resolution, so Reassign's pinned and inherited labels (issue #126) read a skipped model as unset, matching what launches.

**Effort follows the same rule.** It is the same harness-native word on the same code path (ADR-0028). Fixing only the model would leave the same report waiting for effort.

**The resolver runs the same rule over its own four layers**: the Merger's own Assignment, console.json's `resolver`, the pool defaults and the Machine defaults, through the same core helper. Its harness comes from the Merger, then `resolver`, then the Machine defaults, never from the pool defaults, as before. Ownership is still the nearest lower layer that sets a harness, the pool defaults included: `resolver { "model": "auto" }` under `defaults { cursor, auto }` is cursor's word, and a claude Merger never takes it.

**The resolver fails at boot when the rule leaves it no model.** A resolver with a harness, named by its own key or by the Merger's own Assignment or taken from the Machine defaults, that resolves no model because each model it could take belongs to another harness, is a config error. Boot stops before anything launches, with an error that names the resolver, says which layer's model was skipped and for which harness, and gives the object form to write, `{ "harness": "claude", "model": "..." }`. A Merger's error names the fixes reachable from a failed boot: its `conflict.resolver` in `line.json`, or a console.json `resolver` it inherits. A Config reload that would introduce it is rejected whole and the previous config stands, as every invalid reload is (ADR-0018). A Settings save is not checked. A Machine defaults save reloads only a console.json that changed, and every pool on the machine reads the same Machine defaults. So a resolver that fails anyway at its conflict, after the Machine defaults changed under a running pool, takes the manual path, and the merge-conflict Interrupt carries the error. Beginning a Line and editing its Plan refuse a Merger the rule leaves no model, so a Plan the engine accepts never fails at its first conflict. Boot and reload check a Line's Mergers only while it can still merge: a Done or Closed Line is not checked. A resolver with no usable harness at all keeps the manual path. The string form `"resolver": "<harness>"` keeps working when that harness owns the model it falls back to.

**A Ticket uses its Config interrupt instead (ADR-0022, issue #118).** An assign entry or a Line node's Assignment that switches harness without a model resolves to an empty model, and the Ticket waits on the Config interrupt that names it, says which model was passed over and for which harness, and asks for an assign entry with a model of its own, since `defaults.model` cannot fix it. One bad entry pauses one Ticket and never stops the pool. A grader, which the engine launches itself and never schedules, is not launched with no model: its build ticket waits on the same Config interrupt, naming the grader, and resuming it runs a fresh verify round on the config as it then stands. The resolver has no card of its own to show the error on, which is why it fails fast and a Ticket does not. A Conversation's start already refused an empty model; it now also says which model it skipped and for which harness.

**Considered Options**:
- Failing boot for an assign entry too, as the issue asked. Rejected: it would make one Ticket's gap stop the whole pool, the outcome ADR-0022 removed.
- Translating a model name between harnesses, or copying it across "to be helpful". Rejected for the reasons ADR-0028 gave for effort: every translation is a guess, and the operator never typed the result.
- Per-harness default models, such as `defaults.harnesses.claude.model` or a per-harness line in `~/.issue-runner`. Deferred as a follow-up. It adds a fifth layer and a Pool settings field, and the object form on each entry is enough for the mixed pool in the issue.

**Consequences**:
- A pool config that used to inherit a model across harnesses now needs a model of its own on the entry that switches harness. The conformance cases that relied on it (a resolver stub harness under defaults on another stub) need a resolver model of their own.
- A resolver naming a harness this machine lacks now fails boot and reload at load, where the pool used to die at its first conflict.
- A pool with no `resolver` key whose Machine defaults name a harness other than the pool defaults', and no model of their own, now fails boot instead of launching that harness on the pool defaults' model. `"resolver": "none"` keeps the manual path.
- The `my-console-runner` skill checks the written config after boot and asks the operator for the resolver's model, and for any assign entry's model, when the harness changes.
- Validating that a model name exists for its harness stays out of scope. Enlisted panes still run as found, so the rule never applies to them.
- Known follow-ups from the review of issue #37, left outside it: a grader re-spawned between verify rounds resolves its Assignment again without the missing-model check of the first round, so a reload between rounds can leave it no model and fail the drive; a grader's Config or Crash interrupt still shadows a paused round's Checkpoint, as on main; CONTEXT.md's Config interrupt entry does not yet describe the grader variant; the Boot wizard prefills the harness and the model from the Machine defaults independently, so it can pair them across harnesses; and a Settings save that leaves a resolver no model is written, so a Pool settings save the reload refuses stands on disk for the next boot to fail on.
