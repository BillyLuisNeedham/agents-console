# The operator adopts a finished candidate from a paused round: Adopt is its own answer

ADR-0034 made a verify round that holds a paused candidate checkpoint the Ticket, and left the finished candidates' branches waiting unmerged. The operator could Resume (a fresh fan-out), Close (drop the Ticket) or Keep talking (continue the paused candidate). None of these took the work that was already finished and graded. Often that work is what the operator wants: the paused agent asked a question the finished one had answered well enough. Taking it meant a whole new round, or merging the branch by hand outside the engine. ADR-0034 rejected adopting a finished candidate there because it needed its own answer, and this ADR is that answer.

**Adopt is an answer to a paused round's checkpoint.** The checkpoint Interrupt of a verify round that holds a paused candidate offers Adopt beside Resume, Close and Keep talking: one Adopt per finished candidate, each naming its Attempt. The answer goes through the queued-answer path like every other (ADR-0004). It names the Candidate in a field of its own, never in the note. It may carry an optional note, which is recorded on the `answered` event and the pool log as a Close note is, and is never read for a number.

**Only a finished, graded Candidate of the paused round can be adopted.** That is every candidate that finished `done` and got a usable grade, whether its verdict was pass or flag. A flag says the grader had doubts, but the operator has read the Brief and is choosing anyway. A paused candidate, a crashed one and any earlier round's Attempt are refused. When the round checkpoints, the engine records the adoptable Attempts on the checkpoint Interrupt in ascending order, using the `candidates` field a selection Interrupt already carries. It records them only when there is at least one. The list is persisted with the Interrupt, so an Adopt after a restart is checked against the same round. A checkpoint without the list cannot be adopted from: a lone checkpoint, a round where every candidate paused, or a pool checkpointed before this change. Nothing is rebuilt from the events.

**An Adopt is a human selection.** The Interrupt is dropped, and the paused candidate's question with it, unanswered. Its Held pane is let go. The adopted Candidate then goes through the same completion a selection answer uses. Its branch merges, every other Attempt branch and worktree of the Ticket is discarded with its tab (the paused candidate's included), and the Ticket is `done`. Only the adopted Candidate's Outcome becomes the Ticket's, and only its spawn proposals are taken. A conflicted merge checkpoints as a selected Winner's does. The `selected` event uses rule `human`, with the adopted Candidate's grade score, read from the Ticket's log, and a margin of null. Because an Adopt merges, it waits while a Continued attempt holds the pool checkout, as a selection answer does.

**The Steward cannot Adopt.** Picking which finished work lands over an agent's open question is the judgement ADR-0034 kept from the engine, so it stays the operator's. The Steward's teaching never offers Adopt, its command has no word for it, and the engine and the Steward's route refuse it. A Steward that thinks one Candidate should win leaves the checkpoint to the operator with a Steward note saying so.

**Rejected:**
- **Parse the pick from a Resume note.** A selection Interrupt already reads its answer this way, but a Resume note on a checkpoint is free text to the next Attempt and often holds numbers ("try port 8080", "2 is overfit"). Reading a pick out of it would merge work the operator never chose. The pick needs a field of its own.
- **Let the Steward adopt.** It would clear more checkpoints while the operator is away. But it is the same guess-through-the-question that ADR-0034 refused the engine, and a Pool setting like "Steward may Close checkpoints" would only move that guess to the operator's settings. A Steward note recommending a Candidate carries the same knowledge with the operator still deciding.
- **A new `selected` rule value.** `adopted` would separate an Adopt from a selection answer on the log. But the rule says who decided, and here the human did. A new value is a contract change that every reader of the event would have to learn, and the Rust port would have to match. The `answered` event's `action: "adopt"` and the log line already show how the decision was reached.
- **Adopt from any checkpoint by naming a branch.** A lone checkpoint has no rival work to pick between, and an earlier round's branch may already be gone. The persisted `candidates` list keeps the answer to exactly what the Brief showed the operator.

**Consequences:** the contract changes in three additive places. `ResumeAction` gains one value, `adopt`. `ResumeRequest` and `QueuedAnswer` gain an optional `attempt`, required with `adopt` and refused with any other action. `candidates` now also rides on a paused verify round's checkpoint Interrupt, not only on a selection Interrupt. `PROTOCOL_VERSION` stays 1. Every change is an optional field or a new value that a page only sends after seeing the field: an older page ignores `candidates` and shows no Adopt, and a newer page facing an older server sees none and offers none. Close added its action the same way. A queue file written before this change reads as it always did, because both new fields are absent from it. A queued Adopt left in the file when rolling back across this change would be read by an older server as a plain Resume, so drain it first, as with Close (ADR-0033). The Rust port of the engine (issue #162) must carry the new action, the `attempt` field, `candidates` on the checkpoint Interrupt, and the refusals byte for byte.
