# Spawn caps are Pool settings, and a proposal they cannot take is held, not dropped

ADR-0010 made the Spawn caps engine constants: 5 proposals honored per attempt and 20 Spawns per run, with overflow truncated and logged. In the og-review pool that lost work (issue #149, https://github.com/BillyLuisNeedham/agents-console/issues/149). A ticket ended with one proposal: a fix the operator wanted to run before everything else. The run cap was full, so the engine logged `spawn-adopted` with `adopted: []` and `truncated: 1`, and the next ticket started with nothing blocking it. Three things made it worse. The run cap was not really per run: boot counted every ticket on disk with a `spawned-by`, so a restart never reset it. A truncated proposal was gone for good, so raising the cap afterwards could not bring it back. And the only way to raise a cap was a code change and a restart.

**The caps are Pool settings.** Both live in `console.json` as `spawnCaps: { perAttempt, perRun }`. Each field falls back to its old default (5 and 20) on its own and must be a positive integer. They reload at the super-step boundary with the assignment slice (ADR-0018), so the Settings pane edits them without a Restart. A save on a pool with no drive in flight runs that reload at once, because an idle pool reaches no boundary. The prompts teach the caps in force, and the snapshot carries them with this run's count, so the Console can show "Spawns 20/20 this run" before a proposal reaches the cap. They are not Machine defaults: how much a pool may grow is a property of that pool.

**A run is this Console boot.** The count starts at zero at every start. Only Ticket-origin Spawns count against it. A Conversation's own spawn.json batches stay outside the run cap and keep the per-attempt one, as ADR-0018 (Conversations) set.

**A proposal beyond a cap is held, not dropped.** It becomes a Held spawn: the full proposal, its parent, which cap held it, and when. Held spawns persist in `runs/held-spawns.json`, written whole through a rename, and survive restarts. The operator decides each one:
- **Adopt** takes it into the pool past both caps: at the next boundary, or at once on an idle pool, the way a Conversation's spawn.json is adopted. The Adopt is the decision the caps exist to ask for. A Ticket-origin one still counts toward the run.
- **Discard** removes it for good.

An Adopt the pool as it stands would reject is refused up front, and so is one on a pool that has finished, whose store is closed. Either way the spawn stays held. An Adopt queued behind a drive in flight is checked again at the boundary, because the pool may have moved in between (a `blocks` target may have finished). If that check refuses it, the spawn still stays held. The reason is kept on it as `adoptError`, shown by the Console and cleared by the next Adopt, and it goes on the parent's log as a `spawn-rejected` event carrying `fromHeld`. Holds, adoptions and discards all go on the parent's Ticket log.

Two alternatives were rejected. Auto-adopting held spawns when a cap is raised would turn a settings edit into a burst of new work nobody chose one by one. Dropping as before but showing the drop would leave the operator unable to act on what they saw.

**Recovering what was already lost.** At boot, proposals a cap truncated before this change are held as if the cap had held them. The parent's checkpointed Outcome still has its whole `spawn` array. Its last `spawn-adopted` event names the ids adopted and a `truncated` count, which post-ADR adoptions never write. The truncated proposals are the tail of that array once the titles rejected at that adoption are taken out. The rule applies only when the numbers agree and no rejected title is shared by two proposals: titles are all a pre-ADR rejection recorded, and guessing between twins could hold a proposal already adopted. A recovery is recorded with its holds in one write, so it runs once however the operator later decides them. A truncated Conversation batch has no Outcome to recover from.

**A Spawn may block other tickets.** A proposal may carry `blocks`: ticket ids, or `"all"`. When it is adopted, the engine adds the new Spawn to each target's blocked-by, through the same marker write the Enlist form's Blocks uses. `"all"` means every ticket still ready as the adoption lands, sibling Spawns included. It never includes the Spawn itself, anything the Spawn already waits on (that would deadlock), engine-run tickets, or done tickets. A held spawn picks its targets when it is adopted, not when it was held. Named targets must be pool tickets with a next attempt, and must not be anything the proposal waits on. Otherwise the proposal is rejected, as a bad `blockedBy` is. A ticket already running is never interrupted: blocked-by gates its next attempt. No operator approval is needed. The agent already has the authority to shape the pool through `blockedBy`, and `blocks` is the same edge drawn from the other end. A Conversation cannot block anything, so a `kind: "conversation"` proposal with `blocks` is rejected.

**Consequences**: ADR-0010's "overflow is truncated and logged" and its fixed caps are superseded. ADR-0018 (Conversations)'s per-proposal cap of five is now the pool's per-attempt cap. `spawnCaps` joins ADR-0018's reloaded slice. A pool can no longer lose a proposal to a cap. Instead it can collect Held spawns nobody decides, which the Console shows until someone does.
