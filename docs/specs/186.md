# A Continued attempt's checkpoint Outcome drops its spawn array silently, though the prompt says it may propose follow-ups (issue #186)

## Problem

A Continued attempt (Keep talking) on a Ticket that is not a verify Ticket can end with a valid `checkpoint` Outcome that carries a `spawn` array. When it does, the engine takes none of the proposals and records nothing about them: no `spawn-pending`, `spawn-held`, `spawn-rejected` or `spawn-adopted` event, and nothing in the Spawn ledger. In the og-review pool, Ticket `conv-25-spawn-5-spawn-1-spawn-1-spawn-1`, attempt 3 (`continued: true`, `numbered: false`), checkpointed with two schema-valid proposals. Its Ticket log goes `exited`, `checkpoint`, `answered` and nothing else. The operator noticed only because the Tickets never appeared.

The Continued-attempt teaching Turn describes the Outcome as `done` or `checkpoint`, then says "You may propose follow-up tickets in that same outcome JSON by adding a "spawn" array". The agent has no way to know that a checkpoint drops them.

## Cause

`end_continued_attempt` in `crates/engine/src/keep_talking.rs`. On the un-numbered path, at lines 755-764, it calls `take_spawn_proposals` only when `valid.outcome.status == OutcomeStatus::Done` (line 759), and then hands over to `record_adopted_exit` (`crates/engine/src/restart.rs:1006`), which never takes proposals. Every other place that reads a Ticket's Outcome takes them whatever the status:

- the numbered (verify Ticket) Continued path in the same function, on a checkpoint at `keep_talking.rs:806-808`;
- a launched attempt's ending, `join_at_exit` in `crates/engine/src/drive.rs:528-541`;
- the verify flow, `take_proposals` in `crates/engine/src/verify.rs:1065-1072`.

The teaching text is `build_continued_teaching` in `crates/core/src/verify_prompts.rs:196-245`. It is accurate once the engine takes proposals on a checkpoint, so it does not change.

## The change

Take a Continued attempt's Spawn proposals from any valid Outcome it ends with, `done` or `checkpoint`. This is the issue's recommended option. A checkpoint that hands work to new Tickets ("pause this, do these first") is a normal thing to ask for, and both the numbered Continued path and a launched attempt's ending already allow it.

- In `end_continued_attempt`, the un-numbered branch keeps its other guards (not numbered, no `crash_reason`, `read` is `Ok`, a non-empty `spawn`) and drops only the `status == Done` condition. The call stays where it is now, before `record_adopted_exit`. The done path's event order therefore stays as it is, and a checkpoint's attempt events become `spawned`, `spawn-pending` (or `spawn-held` / `spawn-rejected` as `take_spawn_proposals` decides), `exited`, `checkpoint`.
- An Outcome that fails validation, or an ending with a `crash_reason` (pane gone, TUI exited), still takes nothing. This is unchanged.
- Update the doc comment above `end_continued_attempt` (lines 579-585) so it says that a valid Outcome's proposals are taken whether it is done or checkpoint.
- No change to the teaching Turn, the Outcome schema, the protocol types, any ADR or `CONTEXT.md`. The fallback the issue describes (a `spawn-rejected` event with the reason "a Continued attempt's checkpoint does not take spawns", plus a prompt change) is **not** to be built.

## Acceptance criteria

1. In `crates/engine/src/keep_talking.rs`, the un-numbered Continued path calls `take_spawn_proposals(session, ticket_id, proposals, SpawnKind::Ticket)` for a valid `checkpoint` Outcome with a non-empty `spawn`, as it already does for `done`.
2. New Rust unit test in the `tests` module of `keep_talking.rs`, built on the existing `continuing` helper. Give the helper's session a working spawn store by setting `s.pool_dir` to the temp dir and `s.spawn_proposals = ac_core::spawn_proposals::load_spawn_proposals(&runs)`, either inside `continuing` or in the test. Write a valid checkpoint Outcome with a `brief` and one proposal (`title`, a `body` of at least 20 characters, `blockedBy: []`), then call `end_continued_attempt(&mut s, "01", 2, ContinuedEnding::Outcome)`. Assert:
   - the attempt-2 events, by kind, are `SpawnPending`, `Exited` (status `checkpoint`), `Checkpoint`, and the `SpawnPending` payload names the proposal's title;
   - `s.spawn_proposals.pending()` holds exactly one entry, whose parent is `01`;
   - Ticket `01` is `Checkpoint` and there is one `checkpoint` Interrupt on it.
3. A second unit test, or a case inside the same test, covers a `done` Outcome with one proposal: it still produces a single Pending spawn and Ticket `01` is `Done`. This guards against a regression.
4. A crash ending with the same checkpoint-plus-spawn Outcome takes nothing. Use `ContinuedEnding::PaneGone` or `Exited` with an Outcome that fails validation, for example `status: "finished"`. Assert `s.spawn_proposals.pending()` is empty and there is no `SpawnPending` event.
5. Existing unit tests in `ac-engine` and `ac-core` still pass, including `a_continued_attempt_ends_as_typescript_records_it_for_every_outcome_and_ending` and `a_continued_teaching_says_who_chose_to_carry_on`.
6. New conformance case in `conformance/cases/interrupts-keep-talking.test.ts`, area `"interrupts"`, named exactly `a Continued attempt's checkpoint Outcome takes its spawn proposals`. Use the file's `checkpointed(t)` rig and `expectContinued(server, "01", 2)`. Then `writeOutcome(world, "01", { status: "checkpoint", summary: "pause", commitSha: null, brief: "do the follow-up first", spawn: [{ title: "Follow-up", body: "A body long enough to stand as a ticket.", blockedBy: [] }] })`. Assert:
   - a fresh `checkpoint` Interrupt on `01` whose body is the new brief, and `01.md`'s status is `checkpoint`;
   - Ticket 01's attempt-2 event kinds, in order (excluding `spawned`), are `spawn-pending`, `exited`, `checkpoint`, and the `spawn-pending` payload equals `{ pending: [{ id: "proposal-1", title: "Follow-up" }] }`;
   - the proposal lands: within 30 s `issues/01-spawn-1.md` exists, and 01's log has a `spawn-adopted` event whose payload equals `{ adopted: ["01-spawn-1"], fromPending: ["proposal-1"] }`. This mirrors `spawns-blocks.test.ts`, "adopts a checkpoint attempt's proposals while the run pauses on the interrupt".

   Use `{ timeoutMs: 120_000 }` like its neighbours. Import only from `protocol/` and the conformance harness (AGENTS.md, ADR-0036).
7. The other cases in `interrupts-keep-talking.test.ts` still pass unchanged. In particular, the teaching Turn's bytes do not change.
8. `cargo clippy --workspace --all-targets -- -D warnings` and `cargo fmt --check` are clean.

## Out of scope

- The fallback option (record `spawn-rejected` for a dropped checkpoint proposal and say so in the prompt). Not built.
- Enlisted Tickets. `end_enlisted_attempt` in `crates/engine/src/enlist_flow.rs:1079-1094` also takes proposals only on `done`, for an enlisted attempt and for its Continued attempts, while the enlist teaching makes the same promise. That is the same kind of gap but a separate change. Leave it, and note it in the PR body as a follow-up.
- Teaching agents that a proposal cannot name another proposal's future id in `blockedBy` (the issue's notes). `spawns.rs` drops that on purpose. Any change to the prompt wording is a separate issue.
- #185 (an Outcome written into a Held pane is never read).
