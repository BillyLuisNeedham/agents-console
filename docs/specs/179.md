# A harness the pane cannot find at launch (exit 127) crashes the Launch at once: five launches died in six minutes while claude auto-updated (issue #179)

## Problem

When the pane's shell cannot find the harness binary, the wrapper runs (`script` starts, so the Stream file appears and the Launch counts as landed), the harness command fails with 127, and the Launch ends at once as `harness exited 127`. Nothing retries it. A Ticket Attempt becomes a crash Interrupt; a Conversation is marked crashed and its worktree and branch are discarded, so the operator starts it again by hand. On 5 Oct (pool `2160379c`) this happened five times in 6 min 10 s while claude's auto-updater replaced `~/.local/bin/claude`'s target: every failure ended 35 to 50 ms after its `spawned` event, with an empty log, `logTail: []` and an exit-code file holding `127`.

## Cause

The issue cites the deleted TypeScript engine; the same logic now lives in the Rust engine:

- `crates/engine/src/attempt_run.rs:520-596`: the Launch's try loop retries only a wrapper that never ran (`wait_for_wrapper_landed` false); `if landed || try_number >= LAUNCH_TRIES` (line 561) breaks out as soon as the wrapper landed. `LAUNCH_TRIES = 3` (line 172).
- `crates/engine/src/pane_session.rs:268-283`: `wait_for_wrapper_landed` counts the Stream file or the exit-code file as landed, so a 127 is "landed".
- `crates/engine/src/attempt_run.rs:1238-1242`: the readiness wait ends `Readiness::Exited` and the Launch ends `AttemptHandleState::Ended { code: 127 }`, after `spawned` was recorded.
- `crates/engine/src/attempt_ending.rs:391-410`: `exit_crash_reason` renders any real code as `harness exited 127`; it is called from `await_attempt` (`attempt_run.rs:873-888`) and from the Conversation start (`crates/engine/src/conversations/start.rs:330`).
- `crates/engine/src/conversations/start.rs:314-361`: a Conversation whose Launch ended writes `crashed` and calls `git::discard_worktree` (line 360). The wrapper itself is `pane_session.rs:204` (`interactive_wrapper`); on darwin `RESIZE_RELAY` (line 167) ends in `exec "$@"`.

## The change

Decisions (the issue left these open; all are final):

1. **A harness not found is a Botched launch, detected before `spawned`.** The `spawned` event keeps naming only the tab the Launch ended up in. After the wrapper lands, each try runs a short **exit probe**: it polls the exit-code file every `landed_poll_ms` for up to `exit_probe_ms` (new `LaunchCadence` field, default 1_000 ms). If the file appears and reads 127, the try is botched as "harness not found"; if it appears with any other code, or does not appear within the window, the loop ends as it does today. The probe never ends early; it adds at most 1 s before `spawned` on every terminal-backed Launch.
2. **Retry with backoff, its own budget.** A not-found try is retried into a fresh tab like a wrapper that never ran: the botched tab closed with `tab.close` (as now), and a `launch-retried` event with the existing payload shape `{ try, pane_id, tab_id, reason }` where `reason` is exactly `harness not found (exit 127)` and `try` is the Launch's overall try number. Before the next tab opens the Launch sleeps a backoff: 15 s, doubling each not-found retry (15, 30, 60, 120, 240 s), with `NOT_FOUND_TRIES = 6` tries in all (about 7 min 45 s, longer than the 6 min 10 s window observed). The first backoff is a new `LaunchCadence` field `not_found_backoff_ms` (default 15_000) so tests run in milliseconds. A wrapper that never ran keeps its own budget of `LAUNCH_TRIES = 3` immediate retries, unchanged; a try counts only against its own reason's budget.
3. **The last try is an ordinary pre-ready exit.** When the not-found budget is spent, the loop breaks as landed: `spawned` is recorded for that tab, the readiness wait sees the exit-code file, and the Launch ends `Ended { code: 127 }` with its pane kept, exactly as today. A Ticket then crashes with its crash Interrupt; a Conversation is marked crashed and its worktree and branch go, only now after every try failed. No new path in `conversations/start.rs` is needed: `launch_attempt` returns only after the tries.
4. **Shutdown.** Before sleeping a backoff and again after it, the Launch reads the child tracker's `stopping` flag on the host (`on_registries`). Stopping before the sleep: no retry, the try is treated as the last (decision 3). Stopping after the sleep: no new tab is opened and the Launch returns the same engine-gone error its event appends already return when the session is gone.
5. **Crash reason.** Any Launch that ends `Ended { code: 127 }` (the exhausted case, or a 127 that arrived after the probe window but before the ready frame) gets the crash reason `harness "<command>" was not found on the pane's PATH (exit 127)`, where `<command>` is the first word of the interactive argv (`claude`). The word is always `harness`, also for a resolver Launch. Add one helper in `attempt_run.rs` that both `await_attempt`'s `Ended` branch and `conversations/start.rs` use, so the two sites cannot drift. A 127 from a harness that went live and later exited stays `harness exited 127`. The `exited` and `crash` events keep `code: 127`.
6. **Not retried:** 126 and every other code before readiness (the issue's open question on 126 is decided no), a 127 after the probe window, headless Launches (out of scope), and `DISABLE_AUTOUPDATER` (rejected in the issue).
7. **Glossary.** Update the **Botched launch** entry in `CONTEXT.md`: also a Launch whose harness command the pane's shell could not find (exit 127 within moments of the wrapper running), retried with a backoff of minutes, not at once. Update the comment above the try loop (`attempt_run.rs:503-508`) to match. No new ADR.

Files expected to change: `crates/engine/src/attempt_run.rs`, `crates/engine/src/pane_session.rs` (cadence fields, the probe helper), `crates/engine/src/conversations/start.rs` (use the shared crash-reason helper), `crates/engine/src/attempt_run/tests.rs`, `crates/engine/src/conversations/tests.rs`, `CONTEXT.md`, and new conformance cases in `conformance/cases/attempts-terminal-launch.test.ts` and `conformance/cases/conversations-lifecycle.test.ts`. No protocol type changes (`launch-retried` already exists), so `protocol/*.ts` needs no regeneration.

## Acceptance criteria

1. A terminal-backed Ticket Launch whose exit-code file reads 127 within the exit probe is retried into a fresh tab: the botched tab gets `tab.close`, the log reads `scheduled, launch-retried, spawned, exited` with the retry's `reason` exactly `harness not found (exit 127)`, `spawned` names the second tab, and the Ticket ends `done`.
2. The retry waits the backoff: the second `tab.create` comes no sooner than 15 s after the first try's `launch-retried` with default cadence.
3. A Conversation Launch gets the same retries: after one not-found try, `POST /api/conversations` answers `live` on the second tab, its log reads `launch-retried, spawned`, and its branch exists.
4. When all `NOT_FOUND_TRIES` tries read 127, there are `NOT_FOUND_TRIES - 1` `launch-retried` events with try 1 to 5, then `spawned` for the last tab; a Ticket's `crash` reason is `harness "claude" was not found on the pane's PATH (exit 127)`; a Conversation ends `crashed` with that reason and its worktree and branch are removed only after the last try (they still exist after the first `launch-retried`).
5. A Launch whose harness exits 126 (or 3) before readiness is not retried: no `launch-retried`, crash reason `harness exited 126`.
6. A 127 arriving after the probe window but before the ready frame is not retried and its crash reason is the not-found sentence.
7. A wrapper that never ran still gets exactly 3 immediate tries ending `launch command never ran` (existing cases keep passing unchanged).
8. A shutdown during a backoff opens no further tab.
9. Unit tests in `crates/engine/src/attempt_run/tests.rs`, using a `LaunchCadence` with millisecond `exit_probe_ms` and `not_found_backoff_ms` and a fake daemon that writes `127` to the exit-code file when the wrapper is sent, cover 1, 4 (Ticket), 5, 6, 7 and 8, plus the crash-reason helper. An engine test in `crates/engine/src/conversations/tests.rs` with a fast cadence via the engine options' `launch_cadence` covers 4 for a Conversation, including the worktree surviving the retries.
10. New conformance cases (ADR-0036; they import only from `protocol/`), all driven by replacing the world's stub `<root>/bin/claude` with a shim (never by deleting it: the world's PATH also holds `/usr/bin`, where a real claude could be found): in `attempts-terminal-launch.test.ts`, (a) criterion 1 and 2 with a shim that exits 127 at once until the case sees the first `launch-retried`, then the original wrapper restored; (b) criterion 5 with a shim exiting 126; (c) criterion 6 with a shim that sleeps 3 s then exits 127 and a fake herdr that renders no ready frame. In `conversations-lifecycle.test.ts`, (d) criterion 3 the same way as (a). Mark (a) and (d) `{ slow: true }`. The exhausted path (about 8 minutes, and each case runs twice) is left to the unit and engine tests.
11. `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test` pass.

## How Prove shows it working

From the repo root:

1. `cd ui && ~/.bun/bin/bun install && ~/.bun/bin/bun run build && cd ..`
2. `cargo build --release`
3. `cargo test -p ac-engine attempt_run` and `cargo test -p ac-engine conversations`, then `cargo test` for the workspace.
4. The new and neighbouring conformance cases only: `~/.bun/bin/bun run conformance conformance/cases/attempts-terminal-launch.test.ts conformance/cases/conversations-lifecycle.test.ts` (a few minutes). The case titles should contain `exit 127` or `not found` so `-t 'exit 127|not found|126'` can narrow a rerun.
5. Show the evidence: the `events.jsonl` lines (or `readEvents` output) for criteria 1 and 3, with the `launch-retried` reason and the gap between `tab.create` calls.
6. Optionally the full suite, `~/.bun/bin/bun run conformance` (about 50 minutes), to confirm nothing else moved because of the 1 s probe.

## Out of scope

- `DISABLE_AUTOUPDATER=1` or pinning a resolved `versions/<v>` path (rejected in the issue).
- Retrying 126 or any other code; headless Launches; a 127 after a harness went live.
- Any change to how the Console shows `launch-retried`, and any request timeout on `POST /api/conversations` (the start request stays pending for the retries, up to about 8 minutes).
- Detecting the updater, or removing the Ticket from the Console while it backs off.
