Lesson 3 · Agent graphs

Edges and conditional routing

Lesson 2 gave you the state half of the story. This lesson is the control half: who decides what runs next, and how that decision is expressed as data you can read, draw, and audit.

The one-sentence idea

Nodes do the work; edges say what happens next — and an edge is just a function over state. "Nodes and Edges are nothing more than functions — they can contain an LLM or just good ol' code." LangGraph Graph API

Normal edges: the fixed path

If you always go from A to B, write it down: graph.addEdge("a", "b"). Two virtual nodes frame every graph: START marks where input enters (graph.addEdge(START, "a")) and END marks termination. They are reserved names — "__start__" and "__end__" under the hood. Graph API — Edges

Two consequences worth internalising:

  • Multiple edges from one node fan out. If A has edges to B and C, both run in parallel in the next super-step — which is why reducers (lesson 2) exist. Graph API — Edges
  • Multiple entry points are legal. Two edges from START means two nodes run in the first super-step. There is no implicit first node; an unreachable node fails at compile time. graph.ts — validate

Legacy note: older code uses setEntryPoint/setFinishPoint. They still exist as deprecated aliases for addEdge(START, …) / addEdge(…, END); the current docs no longer mention them. graph.ts

Conditional edges: routing as a function

When the next step depends on what happened, use addConditionalEdges(source, routingFunction). The function receives the current state (and runtime config) and returns a node name, END, or — for fan-out — an array of node names that all run in parallel next super-step. Graph API — Conditional edges

An optional third argument, the path map, decouples the function's return value from node names — the function returns a verdict like "approved", the map translates it to a destination: Graph API — Conditional edges

graph.addConditionalEdges("review", route, {
  approved: "implement",
  rejected: "revise",
});

Failure modes, verified in source: returning undefined or a missing path-map key throws "Branch condition returned unknown or null destination"; a truthy but nonexistent node name fails at runtime with InvalidUpdateError. Routing bugs are loud, not silent. graph.ts — Branch

Loops need an exit — and a seatbelt

An edge from B back to A creates a cycle. That is the agent loop from lesson 1, drawn explicitly: the conditional edge is the loop's termination condition, routing to END when the work is done. Use the Graph API — Create and control loops

The seatbelt: LangGraph counts super-steps, and after 25 by default it raises GraphRecursionError. A loop without a reachable exit is a compile-clean, runtime-loud bug. Raise it with the recursionLimit config key (not inside configurable). Graph API — Recursion limit

Command: update state and route in one step

A node can return a Command instead of a plain partial update: update merges into state as usual, and goto picks the next node(s) — routing decided inside the node rather than by a separate edge function. Graph API — Command

graph.addNode("review", (state) => {
  return new Command({
    update: { approval: "approved" },
    goto: "implement",
  });
}, { ends: ["implement", "revise"] });  // declare possible destinations

The docs' rule of thumb: routing only → conditional edge; routing plus state update → Command. And a warning repeated three times in the docs: never mix both from the same node — a static addEdge and a Command goto from the same source will both execute. Graph API — Command

Its sibling Send fans one node out into many parallel invocations, each with its own private input — the map-reduce primitive. That is lesson 4 territory. Graph API — Send

Back to your pipeline

Your grill → spec → tickets → implement flow is mostly fixed edges — the sequence is predefined. The interesting question is where the conditional edges hide: the approval gate after spec (approve → implement, reject → grill again), the per-ticket review loop (pass → next ticket, fail → rework). A graph runtime makes exactly those branch points — and only those — explicit, testable functions over state.

Retrieval practice

Answer from memory before clicking. The feedback is immediate; getting it slightly wrong is useful.

1. Node A has two normal outgoing edges, to B and C. What runs?

2. What does a conditional edge's routing function receive?

3. A node returns Command(goto: "d") and you also wrote addEdge("a", "b") from it. What happens?

4. What is LangGraph's default recursion limit?

Five-minute design exercise

  1. Draw your grill → spec → tickets → implement pipeline as fixed edges only. Where does it enter (START) and where can it end?
  2. Mark every place a human or model actually decides the next step (approval, review verdict, "more questions needed"). Each is a conditional edge — write its routing function as one line of pseudo-TypeScript: (state) => state.approved ? "implement" : "revise".
  3. Pick one routing function: should it be a conditional edge or a Command? Apply the rule — routing only, or routing plus a state update?
  4. Your review loop cycles per ticket. What is its termination condition, and what saves you if the model never converges?
  5. Write one sentence: "The sharpest conditional edge in my workflow is ___ because ___."

Reply to the agent with your edge sketch and ask it to find the routing function you missed. Ask follow-up questions whenever a term still feels fuzzy.
