Lesson 2 · Agent graphs

State and reducers

In lesson 1 you saw that a graph makes control flow and state explicit. Now the crucial detail: how updates from nodes merge into state. That mechanism — the reducer — is where most graph-design decisions actually live.

The one-sentence idea

State is the run’s shared snapshot; each key in it is a channel with its own rule for merging updates. Nodes receive the current state, return a partial update, and the runtime merges each key using that key’s reducer: (current, update) => newValue. LangGraph Graph API

Nodes return partial updates, not whole state

A node does not return the whole state — just the keys it wants to change. If no reducer is defined for a key, the default is overwrite: last write wins, the old value is discarded. Graph API — Reducers

{ foo: 1, bar: ["hi"] } → node returns { foo: 2 } → state is { foo: 2, bar: ["hi"] }
Then a node returns { bar: ["bye"] } → state is { foo: 2, bar: ["bye"] }

Notice bar was overwritten, not appended. If you want accumulation, you must say so — that is exactly what a reducer is for.

What a reducer is

A reducer is a binary function: the left argument is always the accumulated state, the right argument is always the latest node update. It answers one question per key: when a node gives me a new value, how do I combine it with what I already have? Graph API — Reducer arguments

Overwrite (default) Keep the update, discard the old value. Right for: current plan, status, approval decision, last error.
Append / accumulate Merge old and new. Right for: message history, findings, completed tickets, log of attempts.
Custom merge Any rule you need: dedupe by id, keep max, sum counts, merge objects field-by-field.

The canonical example: messagesStateReducer

LangGraph’s prebuilt messagesStateReducer is the reducer you’ll meet most. It does more than append: it tracks message IDs, replaces a message when an update shares its ID, appends new IDs, and supports deletion via RemoveMessage. messages_reducer.ts

Why the ID-tracking matters: with a naive concat reducer, a human editing a message during an approval interrupt would duplicate it instead of updating it. The reducer exists so that updates-by-ID and human-in-the-loop edits stay correct. Graph API — Working with messages

In TypeScript

const State = Annotation.Root({
  plan: Annotation<string>,                    // overwrite
  findings: Annotation<string[]>({              // accumulate
    reducer: (current, update) => [...current, ...update],
    default: () => [],
  }),
  messages: Annotation<BaseMessage[]>({
    reducer: messagesStateReducer,              // append + update-by-id
    default: () => [],
  }),
});

Heads-up: the current docs have moved the recommended API to StateSchema (with ReducedValue, MessagesValue, and Zod fields) and label Annotation.Root as legacy. The mental model is identical — a key plus a merge rule — so learn the model first; the syntax is a detail. Graph API — Schema

Why reducers exist: the super-step

Nodes that run in parallel belong to the same super-step. Each sees the state snapshot from the start of that super-step — not each other’s writes. Their updates are merged afterward, key by key, by the reducers. Graph API — Graphs

Consequences the docs call out:

  • Two parallel nodes writing the same key with no reducer: one write wins, and the order is not guaranteed. If ordering matters, write to separate keys with an ordering value. Use the Graph API — parallel nodes
  • A super-step is transactional: if any parallel branch throws, none of that super-step’s updates are applied.

So the reducer is not bookkeeping detail — it is your conflict-resolution policy for concurrent work. In your handoff pipeline, the equivalent question is: when two agents touch the same artifact, whose edit survives?

Three pitfalls to carry forward

  • Don’t mutate state inside a node. Return updates; let the reducer merge them. Mutating the snapshot is explicitly warned against. Use the Graph API — Define and update state
  • Design nodes for re-execution. With a checkpointer, a resumed node re-runs from its start — appending to a database or re-sending a message can corrupt state. Make node side effects idempotent. Graph API — Nodes
  • Keep runtime config out of state. User IDs, model choices, and feature flags belong in runtime context, not the state schema — otherwise every checkpoint bloats with parameters. Graph API — Runtime context

Retrieval practice

Answer from memory before clicking. The feedback is immediate; getting it slightly wrong is useful.

1. A node returns { foo: 2 } and foo has no reducer. What happens to the old value?

2. What is the signature of a reducer?

3. Two parallel nodes write the same key, no reducer defined. What applies?

4. Where should a model-choice flag live?

Five-minute design exercise

  1. List the keys your grill → spec → tickets → implement state would need (e.g. questions, spec, tickets, reviews, approval).
  2. For each key, write one word: overwrite or accumulate.
  3. Pick the one key where overwrite would bite you — where a second node’s update would silently erase real work. What reducer fixes it?
  4. Imagine a human edits the spec during an approval pause. Would your spec channel handle that edit, or duplicate/lose it?
  5. Write one sentence: “The reducer for ___ is my policy for ___.”

Reply to the agent with your channel list and ask it to attack your overwrite/accumulate choices. Ask follow-up questions whenever a term still feels fuzzy.
