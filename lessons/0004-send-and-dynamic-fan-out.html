Send and dynamic fan-out

Lesson 3 ended on a sibling of Command: Send. This is the map half of map-reduce — one node per item, each with its own private input. It is the graph form of your narrow-context ticket handoff.

The one-sentence idea

Send schedules a node for the next super-step with a payload you choose — not with the shared state snapshot. Return a list of them from a conditional edge (or from Command.goto) and every item runs in parallel. The reducer on the result channel is the reduce. LangGraph Graph API — Send

Same snapshot vs private input

Two outgoing edges from A to B and C is already fan-out. Both nodes run in the next super-step, and both see the same starting snapshot. A conditional edge that returns ["b", "c"] does the same thing. Graph API — Edges

Send exists for the other case: you do not know how many workers you need until you see the list, and each worker should see only its item. That is the docs' stated reason — “different versions of State to exist at the same time.” Graph API — Send

Multiple edges Fixed destinations. Same snapshot. Use when B and C are different kinds of work on the same run.
Send Runtime destinations. Private input per item. Use when N copies of the same node each need a different slice.
Command.goto Same two mechanisms, returned from inside a node, optionally with a state update. Do not also attach a static edge from that node. Graph API — Command

In TypeScript

const fanOut = (state: typeof State.State) =>
  state.tickets.map((ticket) => new Send("implement", { ticket }));

graph
  .addNode("plan", plan)
  .addNode("implement", implement)   // sees { ticket }, not the whole run
  .addEdge(START, "plan")
  .addConditionalEdges("plan", fanOut)
  .addEdge("implement", "review");   // review runs once after all Sends

The destination does not need a declared incoming edge — only that implement exists via addNode. Misspell the name and you get a runtime InvalidUpdateError, not a compile error. You cannot Send to END. algo.ts — Send packets

The reducer is not optional here

N parallel implement tasks writing findings is the lesson-2 conflict, now on purpose. A plain field is last-write-wins and throws InvalidUpdateError: LastValue can only receive one value per step. The channel must be a reducer. Concat order across tasks is not guaranteed — put the ticket id in the finding if you need to attribute or sort later. Use the Graph API — Create branches

One failing branch discards the whole super-step's updates. With a checkpointer, successful tasks are saved and not re-run; a retried node still starts from the top, so side effects must be idempotent. Use the Graph API — exception handling

One thousand Sends is still one super-step

The recursion limit from lesson 3 counts super-steps, not tasks. Fanning out a hundred tickets costs one step; a loop that maps, reduces, and maps again costs one step per round. Default still 25. Raise it with the top-level recursionLimit config key. Graph API — Recursion limit

Back to your pipeline

Your current runner claims tickets one at a time, each with a fresh narrow context. Send is that handoff drawn as data: plan (or tickets) emits the list; each implement task receives only its ticket; review sees the reduced findings once.

What it would add: parallel implement with isolation, one transactional super-step, a single halt point for Review. What it would not replace: blocking edges between tickets. Those are ordinary sequential or conditional edges. If ticket B cannot start until ticket A finishes, do not Send them together.

Skip Send when you have one ticket, when results must be approved one-by-one before the next starts, or when a Promise.all inside a single node is the whole need. Anthropic's rule still applies: add the primitive only when the explicitness pays. Building effective agents

Retrieval practice

Answer from memory before clicking. The feedback is immediate; getting it slightly wrong is useful.

1. What does each Send pass to its target node?

2. Three implement Sends write findings with no reducer. What happens?

3. A router returns one thousand Sends. What does the recursion limit see?

4. When is Send the wrong tool for tickets?

Five-minute design exercise

  1. List the tickets a typical run of your pipeline would emit. Which ones are independent? Which have blocking edges?
  2. Write the fan-out as one line: (state) => state.tickets.filter(?).map(t => new Send("implement", { ticket: t })). What belongs in ??
  3. Name the reduce channel. What does one implement task return? What does Review see after the fan-in?
  4. Pick one ticket that must not go in that Send list. Write the ordinary edge that replaces it.
  5. Write one sentence: “Send would earn its keep in my workflow when ___ and would be a mistake when ___.”

Reply to the agent with your independent-vs-blocked split and ask it to attack the filter. Ask follow-up questions whenever a term still feels fuzzy.
